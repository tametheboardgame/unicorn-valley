## Purpose

Use Sunbeam Village as the third human review lens in the open-ended R6.5-WP19H1+ final-polish programme and bring the village to the same finished standard as the accepted Moonflower Glade and Moonflower Cottage work.

Sunbeam should read as the valley's detailed, thriving social/commercial hub while remaining visually legible. More life and detail must come from deliberate spatial hierarchy, not from stacking additional independent overlays onto the existing scene.

The area boundary is not a technical boundary. If village feedback exposes a shared/global weakness, identify the canonical shared owner and implement the reusable correction rather than create a Sunbeam-specific workaround.

## Feedback block 1 - analysis findings

The clutter is structural rather than a single cosmetic defect. Sunbeam is currently composed by multiple independently positioned systems:

- the base scene draws the large rectangular village-square surface, broad roads, shop shells, bunting, floating labels and prototype NPC markers;
- production presentation later replaces/adds NPC art;
- environment production adds flower-box and ambient decoration;
- Village Life adds notice board, sundial, bench, map sign, shop-window display and fountain props;
- ambient-population systems add moving residents and small interactions.

Concrete confirmed artefacts include:

- a semi-transparent 1,220 × 690 rectangular square treatment that reads as an unexplained brown block;
- the old main west-east road polyline passing directly through the fountain centre;
- the surviving generic `shopkeeper-marker` star/label;
- overlapping activity around the northern shops from bunting, shop detail, village-life props, labels and resident routes;
- top-heavy density while the lower half of the map is comparatively empty.

The first pass is therefore a composition/layout rebuild that preserves underlying gameplay systems rather than a cosmetic patch over the current arrangement.

### H3.2 structural ownership contract

The H3.2 remediation establishes one structural composition authority for Sunbeam Village:

- `SunbeamVillageLayout.ts` owns canonical coordinates, district geometry, the H3.3 plaza/path network and named visual-layer depths.
- `SunbeamVillageScene.ts` owns all static structural presentation: base/ground, districts, plaza/path network, shop exteriors, fountain, Willow garden, gateway presentation and simple ground accents.
- Each shop exterior is an atomic container rooted at its canonical building coordinate. Windows, awnings, door treatment and labels are children of that root and must not be independently positioned in world space.
- `WorldTraversalPolishManager` retains functional transition detection only for Sunbeam and must not draw Sunbeam paths or gateways.
- `ExplorationPathPolishManager` must not draw Sunbeam paths. H3.3 replaces the scene-owned scaffold in place rather than adding another path layer.
- `R65WorldExperiencePresentationManager` must not add Sunbeam shop exterior props. H3.8 will add final shop/village micro-detail through the H3 composition owner.
- `VisualTighteningManager` must not support Sunbeam Village. Its legacy fixed-coordinate shop-window pass was the source of the detached windows exposed after H3.2 moved the buildings.
- Dynamic systems remain separate by design: Core NPC presentation owns production NPC sprites, Ambient Population owns roaming residents, Village Life owns interactive props, and quest managers own conditional quest markers. Those systems consume canonical layout positions where they touch the rebuilt village.

This contract exists specifically to prevent the detached-window/path duplication failure exposed during H3.2 visual review.

### H3.11 - Village interiors and local content maturity

H3.11 is now an umbrella programme for rebuilding Sunbeam Village interiors as proper playable places rather than static room/menu backdrops. Each substantial location receives its own H3.11.x slice and human approval checkpoint.

**Core design rule:** an interior is a playable world space, not a menu with a picture behind it.

The player should enter through the relevant exterior door, appear inside as their unicorn, move freely around the room, collide correctly with walls/furniture/counters, pass in front of and behind appropriate objects, approach NPCs and interactables using the shared H3.9 interaction ownership, and leave through a clear physical exit. Existing quests, economy, progression, saves and entry/return semantics remain preservation requirements unless a specific H3.11.x slice explicitly changes them.

Interior character presentation must also become spatially coherent. **Outdoor village residents remain outdoor residents; normal shop/home interiors use their own dedicated staff/resident characters rather than reusing the same unicorn inside and outside.** A recurring outdoor character may only appear inside when a later story/state explicitly moves that authoritative presence there. Interior NPCs are assigned by role/state/location, not cloned from the exterior population. Role-specific presentation is encouraged where it makes the world more legible; in particular, the Sunbeam Bakery baker must read unmistakably as the baker, including a proper baker/chef hat and suitable workwear such as an apron.

**Acceptance:** a reusable walkable-interior contract exists and subsequent H3.11.x rooms can use it without bespoke movement, collision, interaction or duplicate-NPC hacks.

##### H3.11.4B - Library catalogue and content architecture — complete

Make the library content-driven so adding stories scales with content volume rather than code volume.

- Define a stable story identity and catalogue metadata model covering at minimum title, subtitle/description, author/credit, cover, series/order where relevant, tags/categories, chapter list, illustration metadata and publication/visibility state.
- Store long-form prose as **separate story/chapter content assets**, not giant TypeScript literals and not one monolithic JavaScript bundle.
- Prefer an author-friendly format such as Markdown plus lightweight metadata/explicit stable block identifiers, with a small parser/loader contract owned by the library system. Structured JSON may be used for manifests, but writing/editing the actual prose should not require hand-authoring large JSON documents.
- Split long works into logical chapters. A novel-length story should not require loading/rendering the entire book just to open its catalogue entry or first chapter.
- Keep a lightweight catalogue/index that can be discovered quickly, while chapter bodies and heavyweight assets are fetched only for the selected story.
- Give content blocks that can hold resume positions stable identifiers that survive ordinary wording changes. Generated page numbers or absolute character positions are not authoritative identifiers.
- Design the content model to support text-only stories, lightly illustrated stories and heavily illustrated stories without separate reader implementations.
- Adding a new conforming story should normally mean adding a story folder/manifest, chapters and optional art; it should **not** require a new scene, service branch or bespoke UI implementation.
- Keep authored long-form books conceptually distinct from dynamic in-game adventure memories where useful, but allow both to appear coherently within the wider Story House catalogue experience.

A target content shape is broadly:

```text
stories/
  story-id/
    book.json
    cover.webp
    chapters/
      01.md
      02.md
    illustrations/
      ch01-01.webp
      ch01-02.webp
```

The exact filenames/schema may evolve during implementation, but the ownership boundary is fixed: **metadata indexes the library; chapter text and images are independently addressable content assets.**

**Acceptance:** the catalogue can represent many books and series without materially increasing core game-code complexity, and a developer can add a representative new story without changing reader code.

##### H3.11.4D - Reading persistence, preferences and completion — complete / human-approved 24 September 2026

Treat reading state as durable player progress and support several books being read in parallel.

- Save an independent resume position for every started story.
- Store position using **story ID + chapter ID + stable block ID + local progress within that block** (or an equivalently stable semantic locator), not page number or one absolute character offset.
- Restore the nearest valid position gracefully if a story is edited and the exact saved block no longer exists.
- Track at minimum not-started, in-progress and completed state plus chapter/book percentage suitable for player-facing progress.
- Expose **Continue Reading** from the Story House catalogue and resume directly at the saved position.
- Persist global reader preferences such as font size and line spacing once rather than per book unless a clear use-case requires overrides.
- Allow multiple stories to retain independent positions simultaneously.
- Record completion in a way that can support catalogue badges and library-wide statistics without coupling story completion to quest completion.
- Preserve save compatibility. If persistence requires a save-schema change, make it a bounded migration with explicit old-save tests rather than silently invalidating existing profiles.

A conceptual state shape is:

```ts
storyReading: {
  "story-id": {
    chapterId: "chapter-03",
    blockId: "ch03-hidden-door",
    blockProgress: 0.42,
    percentComplete: 61,
    completed: false,
    lastReadAt: "..."
  }
}
```

The exact field names are implementation details; the semantic stability requirement is not.

**Checkpoint 1 started 24 September 2026:** move durable reading state into the canonical save contract using schema v9. Persist global typography preferences and independent per-story semantic positions, restore by chapter/block/local progress with a percentage-based nearest-position fallback if authored content changes, expose Continue Reading and status/progress in the catalogue, and record explicit book completion. Add old-save migration and multi-book persistence tests.

**Acceptance:** the player can start several books, leave Story House/gameplay, return later and resume each one independently with correct reader preferences and useful completion status.

##### H3.11.4E - Illustration and media pipeline — human-approved 24 September 2026; technical closeout running
