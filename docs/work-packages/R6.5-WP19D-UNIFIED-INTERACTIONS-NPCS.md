## Scope and execution contract one interaction route and reliable NPC engagement

Autonomy: Amber behavioural contract; implementation follows the approved rule. Dependencies: WP18K and WP19B navigation. Findings: A02/A03/A05/A06.

Registry contract:

- Each provider registers stable ID, semantic action kind, display name, live position, enabled/visible state, reachability/approach and activation callback/result.
- Scene coordinator chooses one eligible candidate and supplies both the visible action and optional direct-tap route. No parsing rendered text to discover an action.
- Prefer an explicitly tapped eligible target; otherwise select the nearest eligible target with deterministic ties and a small retention margin to avoid flicker between neighbours. Do not make a distant high-priority target steal a nearby action.
- Resolve/revalidate the target at activation. Despawn, scene transition or newly locked conditions invalidate it cleanly.
- Input is consumed once. Opening/closing dialogue cannot activate a second object with the same key/tap. Modal state suppresses background movement and interaction.

Migration inventory:

- Core scene targets; all supporting residents; depth objects; discoveries/secrets; story anchors; shop/interior doors; race starts; repeatable activities; home interactions.
- Enumerate every provider with old route, new route, tests and prompt removed. Remove `WORLD_INTERACTION_PROMPT` production use only after coverage is complete.
- World labels may name a character/place or give an authored clue; they must not repeat Talk/press E/tap instructions. Help retains input reference. Generic idle control guidance should be brief onboarding/Help, not permanent clutter.
- Preserve automatic region crossing. Doors that currently require activation remain explicit Enter actions. Do not silently change all gateways.
- Preserve direct tapping as a convenience using the same command; it is not a second visible instruction system. Out-of-range tapping should move to a valid approach where supported, then require the meaningful interaction action unless an established safe interaction flow already does otherwise.

NPC checks:

- Each applicable visible resident has one live interaction target that follows its actual body.
- Engaged NPC stops, faces the player and stays until close; no timeout resume while reading.
- Verify every supporting resident ID and every core role, especially Maple, Echo, Fern and Nova's race/picnic/cottage presence. Add presence authority only for actual conflicting roles.
- Normal movement resumes after close and survives scene leave/return; no duplicate bodies or lingering invisible hit zones.

Validation: two nearby targets, crossing moving residents, tapping during movement, double taps/key repeat, target despawn, modal close, scene return, quest state changes, one activation/event per input. Test with ordinary controls, not solely direct diagnostic callback invocation.

## 2026-09-11 human-review remediation contract

Preserve the parts David confirmed are working: contextual interaction, engaged NPC stop/face behaviour, distance gating and the unified interaction architecture.

Before the next review candidate, complete all of the following:

1. Desktop/laptop control ownership
   - Touch D-pad and Gallop controls must not appear merely because a desktop/laptop has a touchscreen.
   - Primary coarse/touch devices such as tablets/phones retain touch movement controls.
   - Contextual Talk/Interact/Enter/Start remains available on desktop and must not be tied to touch movement visibility.

2. NPC physical presence
   - Player and visible unicorn residents must not pass through each other.
   - Use collider/separation behaviour that is stable for roaming NPCs and does not introduce jitter, trapping or duplicate physics bodies.
   - Engaged NPC stop/facing behaviour remains authoritative while talking.

3. Lower-screen conversation ownership
   - Conversation/speech presentation must not sit beneath or collide with the top HUD.
   - The protected lower-screen speech area is the preferred presentation area.
   - While a conversation is active, contextual target/name/hint UI that normally occupies the same lower area is hidden. Conversation is the sole owner of that space.
   - After close, contextual presentation may return only once the closing input has been consumed/released and the target is still eligible. Do not permit visual overlap or same-input immediate re-trigger.

4. Wonderbook discovery feedback
   - Discovery feedback must not overlap the top HUD or an active conversation.
   - Prefer a smaller contextual treatment near the discovered object/place where practical. Otherwise queue/coalesce it into a safe notification area only when conversation does not own that area.

5. Starlight Beach HUD
   - Starlight Beach must retain the canonical persistent exploration top HUD in the same way as the other supported world scenes.
   - Do not create a Beach-specific replacement HUD.

6. Conversation consistency preparation
   - Equivalent NPC conversation entry must originate from the shared interaction owner.
   - WP19D should provide clean locking/suppression/engagement contracts needed by WP19E.
   - Do not build a temporary return-position/checkpoint mechanism for ordinary conversation-only scene transitions.

7. WP19E hand-off
   - WP19E will retire ordinary conversation-only cutscene/scene transitions entirely.
   - Normal NPC speech, multi-line dialogue, quest hand-ins and choices will remain in the active world scene, with player and speaker visible and movement/background interaction locked.
   - Separate scenes remain valid for actual activities/modes such as races, minigames, creator flows and required interiors/shops. Dialogue length alone is not a reason to change scene.

Done for this remediation when desktop control visibility, NPC separation, lower-screen ownership, discovery placement and Starlight Beach HUD have passed automated checks and David can re-review the corrected candidate without known overlap or interaction-regression defects.
