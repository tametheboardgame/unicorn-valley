# R6.5-WP19H0 - Performance Architecture and Codebase Consolidation

Approved by David on 12 September 2026 after WP19H exposed that the current whole-game 650 KiB gzip safety envelope no longer scales with the planned breadth of Unicorn Valley.

## Objective

Give Unicorn Valley enough architectural and performance headroom for substantial future growth without sacrificing startup speed, mobile/tablet responsiveness or maintainability.

This is not a package to shave arbitrary bytes until CI turns green. It is a deliberate architecture pass that must separate **startup cost** from **total game breadth**, remove accumulated code duplication/legacy residue, improve code-splitting boundaries and replace the current whole-game performance ceiling with a scalable performance policy.

R6.5-WP19H1 must not begin until H0 is complete and accepted.

## Context / why

The existing `scripts/checkPerformanceBudget.mjs` enforces several useful guards, including a hard application-entry budget, but it also sums every emitted JavaScript chunk and fails when the entire game exceeds 650 KiB gzip.

That total includes lazy/on-demand code which is not necessarily downloaded to reach the title screen or first playable state. As Unicorn Valley adds areas, quests, activities, UI, audio systems and future features, treating all possible game code as one fixed download ceiling creates an artificial maximum game size rather than measuring the experience that matters to the player.

WP19H reached this ceiling while adding a small audio/settings feature set, despite the actual audio runtime being only a small fraction of the total bundle. That is the trigger for this package.

## Frozen product invariants

H0 is behaviour-preserving unless a separately recorded defect is discovered and explicitly owned. Preserve:

- save schema and save compatibility;
- quest/progression state and rewards;
- map topology and current travel semantics;
- player movement, tap/click movement and race mechanics;
- canonical WP18I/J exploration UI and responsive behaviour;
- accepted conversation/interaction behaviour;
- WP19H audio behaviour and settings semantics;
- existing content, dialogue and unlocks;
- production deployment gate and human acceptance rules.

Do not use architecture cleanup as permission to redesign gameplay or visuals.

## Required work

### H0.1 - Measured baseline and dependency map

Record a reproducible baseline for the accepted WP19H candidate, including at minimum:

- application entry raw/gzip size;
- Phaser/vendor raw/gzip size;
- JavaScript required to reach the title screen;
- JavaScript required to reach the first playable exploration scene;
- largest lazy chunk;
- total emitted JavaScript raw/gzip size;
- chunk count;
- representative desktop and mobile startup/load timing where existing tooling allows reliable measurement.

Produce an import/chunk ownership map showing which modules are in the initial graph and which are truly lazy.

### H0.2 - Bundle analysis tooling

Add a repeatable bundle-analysis report that makes size growth attributable rather than opaque. CI/evidence must show the largest chunks/modules and meaningful deltas from the accepted baseline.

The report should be cheap enough to run routinely and must not itself ship production debug code.

### H0.3 - Deliberate code-splitting architecture

Audit `src/main.ts`, scene registration and shared imports. Establish deliberate loading boundaries for major areas and heavyweight optional systems where safe, including candidates such as:

- unicorn creator;
- Moonflower Glade/Cottage/Patch;
- Sunbeam Village/interiors/shops;
- Rainbow Meadow and Rainbow Run;
- Crystal Brook/Grotto;
- Whispering Woods/Hollow Tree/Firefly content;
- Starlight Beach;
- Wonderbook/Inventory/Settings and other modal systems where separating them improves the actual initial path;
- activities/minigames and future expansion seams.

Do not split code mechanically if it increases duplicate payloads or harms transition behaviour. Measure before/after.

### H0.4 - Repo-wide consolidation and dead-code retirement

Perform another evidence-led cleanup pass focused on code accumulated after WP18K and residue WP18K could not safely remove. Audit:

- obsolete presentation/compatibility managers;
- dead class fields/functions/imports;
- duplicate constants/helpers;
- old remediation shims superseded by canonical owners;
- repeated scene plumbing that can be shared without creating a god-manager;
- production diagnostic code that should be on-demand or development-only;
- large static data embedded in executable JavaScript where a data asset is more appropriate;
- tests whose only purpose is retired behaviour.

Delete only after tracing ownership/reachability. Preserve regression coverage for real human-observed failures.

### H0.5 - Replace the whole-game-size ceiling with scalable budgets

Redesign `scripts/checkPerformanceBudget.mjs` so hard failures protect player-visible performance rather than imposing a permanent maximum on total game breadth.

The final policy must distinguish at least:

1. **Initial/entry budget** - hard gate.
2. **Startup/first-playable dependency budget** - hard gate.
3. **Largest individual lazy chunk / route-feature budget** - hard gate or tightly controlled exception mechanism.
4. **Total emitted JavaScript** - measured and trended; normally warning/regression evidence rather than a fixed whole-game hard ceiling.
5. **Unexpected duplication/chunk-regression detection** - fail where a change materially worsens loading architecture.

Do not simply replace 650 KiB with a much larger arbitrary total. Derive the new thresholds from measured healthy baselines and leave deliberate headroom for future development. Document the rationale and how future WPs should interpret the metrics.

### H0.6 - Runtime/cache sanity

Verify that code splitting does not create visible stalls or repeated downloads during normal movement through the valley. Confirm fingerprinted assets/chunks remain cacheable and scene transitions fail safely if a lazy module cannot load.

## Acceptance criteria

H0 is complete only when:

- the current bundle/startup architecture is documented with measured evidence;
- the initial and first-playable dependency graphs are explicitly identified;
- major optional/area code is lazy-loaded where it produces a measured benefit;
- meaningful dead/duplicate/legacy code found by the audit is removed rather than hidden;
- the performance script no longer treats all future game code as one immutable 650 KiB gzip ceiling;
- new hard budgets protect startup and pathological chunk growth;
- total JavaScript remains visible as a tracked metric with baseline/delta evidence;
- there is demonstrable headroom for the H1-H13 polish programme and later expansion without weakening player-visible load performance;
- no save, progression, interaction, race, responsive UI or accepted WP19H audio regression is introduced;
- format, lint, type-check, unit tests, production build/static smoke, browser compatibility and the full serial browser playtest are green on the final head;
- `ROADMAP.md`, `STATUS.md`, `PROJECT_STATE.json` and relevant engineering docs describe the new performance contract;
- David reviews the technical evidence and explicitly accepts H0 before WP19H1 starts.

## Non-goals

- No new region, quest pack or daughter-led R7 feature expansion.
- No visual redesign.
- No save-schema migration unless a separately approved blocker makes it unavoidable.
- No removal of test coverage solely to reduce bundle size.
- No arbitrary budget increase presented as optimisation.
- No production deployment without the normal explicit approval.

## Delivery and backout

Use a dedicated branch and PR after WP19H is accepted. Keep refactors in reviewable stages with measured before/after evidence. Where practical, separate structural code-splitting from cleanup so regressions can be bisected.

If a proposed split increases initial transfer, duplicates large shared modules or causes unstable transitions, revert that split rather than forcing it through to satisfy a theoretical architecture target.

## Exit

After H0 receives explicit David acceptance, proceed to `R6.5-WP19H1-H13 - Area-by-Area Final Polish Programme`. The new performance measurements and budgets become the governing performance contract for every subsequent package.
