# R6.5-WP19H0 - Architecture, UI, Test and Performance Consolidation

WP19H0 is the mandatory engineering-consolidation gate between the accepted audio programme and the H1-H13 area-by-area final polish programme.

David expanded H0 on 13 September 2026 from a performance-only architecture pass into a full **behaviour-preserving architecture/codebase, UI-system, scene-standardisation, test/CI and performance consolidation programme**. The expansion is deliberate: H0 should make later area polish and future game growth materially easier, safer and cheaper rather than merely recovering a few bytes of bundle headroom.

Implementation has **not** started. This document is the execution contract for a fresh Work/Codex session.

## Objective

Leave Unicorn Valley with a durable engineering platform in which:

- code has clear owners and dependency boundaries;
- recurring UI is produced by canonical reusable primitives rather than scene-specific copies;
- Phaser-canvas and DOM-overlay controls share one design/layout contract;
- new exploration scenes follow a standard composition/scaffolding recipe;
- scene navigation, return position, persistence, audio, interaction, HUD and teardown use predictable shared contracts;
- tests protect user/product behaviour rather than accidental row indexes, coordinates or implementation details;
- small bounded fixes receive fast targeted feedback while whole WPs/releases still receive full qualification;
- CI explains why a test group ran or was skipped;
- startup/first-playable cost is measured separately from total game breadth;
- optional regions/features are deliberately lazy where measurement shows a benefit;
- transitional/legacy managers and duplicate systems are actually retired once migration is proven;
- future Work/Codex sessions can add a scene or UI surface without rediscovering a different local architecture each time.

H0 is **not** a gameplay rewrite or visual redesign. Accepted product behaviour is the baseline.

## Why this package is needed - current code audit

The 13 September planning audit found several concrete consolidation seams in the accepted `main` baseline.

### Bootstrap and ownership accumulation

`src/main.ts` still acts as a broad composition root for many cross-cutting managers and progressively/lazily registered systems. Some are valid application services, while others are historical presentation, compatibility or migration layers. H0 must identify which genuinely need game-wide lifetime, which belong to scene composition, which should be lazy and which are retirement candidates.

The goal is **not** to replace many managers with one god-manager. The goal is explicit ownership and lifecycle.

### Scene loading is only partly deliberate

`src/game/config/gameConfig.ts` statically imports/registers a substantial set of scenes while `src/main.ts` dynamically adds others. The split is historical rather than a documented loading policy. H0 should establish a scene manifest/registry and measured loading boundaries suitable for deliberate code splitting without changing scene identity or save semantics.

### UI has overlapping design systems

`src/game/ui/uiTheme.ts` and `src/game/ui/ConceptUi.ts` both contain colour/style/layout concepts. Additional DOM controls use separate CSS. The approved visual language is consistent to a player, but the implementation still permits drift because canvas and DOM surfaces do not consume one canonical token/component contract.

H0 should converge recurring UI onto one Unicorn Valley design system rather than adding a third helper layer.

### Existing reusable UI should be preserved and promoted

`DialogueCard`, `WorldConversationPresenter`, the concept UI helpers and other accepted components already contain useful behaviour such as child-friendly sizing, touch targets, responsive positioning and conversation semantics. H0 should refactor toward proven owners where appropriate rather than rewrite working UX for architectural purity.

### Canvas/DOM overlay coordination needs a first-class contract

The WP19H Settings remediation exposed how fragile independent Phaser-row and DOM-control positioning/clipping can be. The audio slider/select manager had to infer Phaser row geometry and viewport visibility. H0 should provide a canonical overlay host/layout/clipping/focus contract so future native HTML controls do not require bespoke frame-by-frame positioning logic.

### Exploration scenes repeat plumbing

`InteractiveMicroLocationScene` demonstrates that useful scene-level composition can be shared, while larger exploration scenes still repeat portions of player/controller/input/interaction/HUD/dialogue lifecycle plumbing. H0 should standardise the composition contract without forcing every scene into a deep inheritance hierarchy.

### Transitional code has explicit retirement intent

`LegacyWorldFeedbackMigrationManager` describes itself as a transitional migration layer that can be deleted once producers use the shared presenter. `DesktopConceptCleanupManager` and similar historical tightening/cleanup owners must also be evidence-led retirement candidates rather than permanent architecture by inertia.

### Test intent is obscured by delivery history

Many browser tests are named after the WP that created them. Recent WP19H remediation also exposed brittle tests that depended on settings-row counts or stale/off-screen coordinates rather than the user contract. H0 should preserve valuable regression evidence while making ownership, intent and selectors semantic.

### CI currently treats most code changes as full-package changes

`.github/workflows/ci.yml` currently runs formatting, lint, type-check, all unit tests, build, performance and static smoke, then all three Chromium browser shards and the compatibility matrix. That is appropriate for final qualification but unnecessarily expensive as the only routine path for a tiny bounded UI/CSS fix.

### Performance policy measures breadth as if it were startup

`scripts/checkPerformanceBudget.mjs` currently hard-fails on the sum of all emitted JavaScript, including lazy chunks, with a 650 KiB gzip ceiling. It also has useful entry/largest-chunk checks. H0 should retain strict player-visible guards while replacing the permanent whole-game breadth ceiling with measured initial/first-playable and lazy-chunk controls.

The accepted WP19H `main` baseline is approximately 650.3 KiB total-JS gzip against that 650 KiB legacy ceiling. H0 must record that inherited baseline explicitly and must not worsen it casually; final H0 qualification must be green under the reviewed replacement performance contract.

## Research basis / implementation principles

The H0 design should follow the capabilities of the tools already used by the repository rather than invent bespoke infrastructure unnecessarily:

- Vitest supports affected-test execution through `vitest related` and `--changed`; these are candidates for fast unit feedback, with explicit force-full triggers for shared configuration/core changes.
- Playwright supports tags/`--grep`, projects and sharding; use those to create stable subsystem/critical-flow test groups rather than copying CI workflows per feature.
- GitHub Actions path filters are useful but are **not** the sole selection mechanism for required checks: skipped required workflows can remain Pending. Keep a stable required classifier/validation workflow and select work inside it.
- Vite dynamic imports and lazy glob imports create separate production chunks. Use measured scene/feature boundaries, not mechanical splitting or tiny-chunk proliferation.
- Native HTML controls should retain native semantics where they are the right tool; styling/overlay infrastructure should not throw away keyboard/focus/accessibility behaviour.
- Prefer composition and explicit dependency ownership over deep scene inheritance.
- Prefer architectural tests/lintable rules over documentation-only conventions when a rule can be mechanically enforced.

## Frozen product invariants

Unless a separately recorded blocker is discovered and explicitly owned, preserve:

- save schema and backwards compatibility;
- quest/progression state, rewards and unlocks;
- map topology and travel semantics;
- player movement, tap/click movement and race mechanics;
- the approved WP18I/J concept-grade UI appearance and responsive behaviour;
- accepted conversation and interaction behaviour;
- accepted WP19H music/SFX/settings behaviour;
- scene IDs relied on by saves, navigation and tests unless a compatible indirection/migration is proven;
- existing content, dialogue and child-facing wording except where test IDs/hidden metadata are added;
- desktop/laptop, tablet landscape, phone landscape and phone portrait support;
- the production deployment and human-acceptance gates.

A refactor that produces a technically cleaner game but changes accepted behaviour has failed H0.

## Execution model

H0 is one umbrella work package and should use one long-lived H0 delivery branch/draft PR, with **small, bisectable checkpoint commits** and Codex tasks scoped to one sub-phase at a time. Do not produce one giant rewrite commit.

Recommended Work/Codex sequence:

1. Work owns the package, evidence, sequencing and gate decisions.
2. Dispatch Codex only against the currently active H0 sub-phase.
3. Require Codex to inspect the existing owner before introducing a new abstraction.
4. Commit each coherent migration/guardrail independently so a regression can be bisected or reverted.
5. Keep the draft PR current with before/after evidence.
6. Do not start H1-H13 while H0 is open.
7. Do not merge H0 or deploy production until H0K is complete and David has reviewed the final technical evidence.

H0A is analysis/evidence only. H0B-D establish the target architecture before broad migration. H0E-G redesign test ownership/selection before H0J removes old structures. H0H addresses measured loading/performance. H0I makes the new standards durable. H0J migrates the remaining code. H0K is full qualification.

## H0B - Architecture boundaries, dependency rules and lifecycle ownership

### Purpose

Define where code belongs before moving it.

### Target boundaries

Use the audit to formalise a practical layering model, expected to resemble:

1. **platform/bootstrap** - browser/Vite/Phaser setup and composition root;
2. **domain/state** - save-compatible game state and pure rules;
3. **application services** - navigation, interaction, audio, persistence orchestration;
4. **scene composition** - scene-specific world/content orchestration;
5. **presentation/UI** - canonical visual and input primitives;
6. **content/assets/generated data** - data rather than executable ownership;
7. **test/diagnostics** - opt-in instrumentation that cannot accidentally become runtime product ownership.

The exact folders may differ if the H0A evidence supports a better fit; the invariant is explicit allowed dependencies and lifecycle.

### Required work

- Document service lifetimes: app-wide, scene-scoped, modal-scoped, transient.
- Replace hidden ownership-by-import side effects where practical with explicit composition.
- Define typed event/domain contracts where stringly/global events currently couple unrelated modules.
- Establish import-boundary/architecture checks for high-value forbidden directions.
- Identify and reduce per-frame global scanning/polling where event/lifecycle registration is safer.
- Keep shared services narrow; do not create a central god object.
- Preserve public/save-facing IDs during consolidation.

### Acceptance

- A canonical architecture document and dependency rules exist.
- At least one representative cross-cutting owner is migrated/proven without behavioural change.
- New forbidden-dependency checks fail intentionally when a prohibited edge is introduced.

## H0C - Unicorn Valley UI design system and canvas/DOM bridge

### Purpose

Make visual/interaction consistency the default outcome of reusable code.

### Canonical primitives to establish

Names may change, but the responsibilities should include:

- button/action control;
- panel/card;
- modal/sheet and modal backdrop/input ownership;
- heading/body/caption typography;
- dialogue/chat surface;
- world message/guidance/reaction surface;
- discovery/reward/notification surface;
- scroll container with clipping and safe viewport boundaries;
- settings/control row;
- range slider wrapper;
- select/dropdown wrapper;
- close/back controls with visible glyph plus protected touch target;
- HUD/status card primitives;
- focus, keyboard, pointer/touch and disabled/selected states.

### Token contract

Converge overlapping `uiTheme.ts`, `ConceptUi.ts` and DOM CSS values onto one canonical token source/contract for:

- palette;
- typography;
- radii;
- border weights;
- shadows;
- spacing scale;
- control heights;
- minimum touch targets;
- z/depth layers;
- responsive breakpoints/safe areas where applicable.

Do not mechanically eliminate useful semantic aliases. Eliminate contradictory sources of truth.

### Canvas/DOM overlay contract

Provide one supported way to place native HTML controls over Phaser UI. It must own:

- canvas-to-DOM coordinate conversion;
- scaling/resizing;
- scroll/viewport clipping and visibility;
- z-order/modal layering;
- pointer propagation;
- focus/keyboard semantics;
- lifecycle creation/destruction;
- responsive/mobile safe areas;
- test selectors/accessibility names.

The Settings audio controls are the reference regression case that the new bridge must solve without bespoke frame-by-frame hacks.

### Migration proof

Migrate a representative set including Settings controls plus at least one recurring canvas-only surface. Do not mass-migrate the game until the primitives prove parity.

### Acceptance

- New recurring UI has one obvious canonical construction path.
- Canvas and DOM controls visually/behaviourally share the approved concept language.
- Representative desktop/tablet/phone evidence shows no UI redesign or regression.
- Accessibility/touch/focus semantics remain intact.

## H0E - Test-suite audit and contract redesign

### Purpose

Make the suite protect what the player/product needs rather than historical implementation details.

### Classify every meaningful test

Each test/file should be classified as one of:

- **critical product contract** - boot, new game, save/load/Continue, core navigation/persistence, critical input;
- **feature contract** - stable observable behaviour for a subsystem;
- **visual/layout contract** - only where automated geometry/visibility is truly authoritative;
- **implementation-detail test** - candidate rewrite/removal;
- **duplicate coverage** - candidate consolidation;
- **historical regression** - retain if the underlying failure remains plausible;
- **obsolete/stale** - remove only with evidence;
- **flaky/environmental** - repair or quarantine with explicit owner, never silently ignore.

### Redesign principles

- Prefer semantic IDs/roles/state over row counts and absolute click coordinates.
- Avoid tests that only restate current implementation structure.
- Use direct domain/unit tests for pure rules instead of opening a browser unnecessarily.
- Keep browser tests for integration/interaction/responsive behaviour that genuinely needs a browser.
- Preserve regression tests for human-observed defects where the failure mode still exists.
- Rename/reorganise WP-numbered tests where doing so materially improves stable ownership; historical traceability can live in comments/metadata rather than the filename.
- Define reusable test helpers/fixtures for common boot, save, navigation, viewport and interaction setup.

### Deliverables

- test-contract matrix mapping user behaviour -> owner -> test level -> CI tier;
- removal/rewrite ledger with rationale;
- explicit list of critical safety-floor tests;
- measured flake/runtime baseline.

### Acceptance

- Every critical player contract has an explicit owner/test path.
- Known brittle WP19H-style index/coordinate assertions are replaced where appropriate.
- Removed tests have documented replacement or evidence that the behaviour is retired.

## H0F - Tiered verification model

### Purpose

Give tiny fixes fast feedback without weakening final confidence.

### Required tiers

The implementation may tune names, but it must preserve this intent:

**Tier 0 - static/architecture**

- formatting of touched files or equivalent fast check;
- lint;
- type-check where TypeScript/runtime code changed;
- architecture/dependency rules;
- project-contract validation where durable docs/state changed.

**Tier 1 - affected unit tests**

- Vitest related/changed selection where dependency analysis is reliable;
- force-full triggers for shared configuration, global test setup, persistence schema/core domain or uncertain dependency edges.

**Tier 2 - targeted browser/subsystem smoke**

- tagged/projected Playwright groups selected by subsystem/change ownership;
- critical safety-floor browser tests when runtime code changes in relevant risk classes.

**Tier 3 - full Chromium qualification**

- complete browser suite, sharded as appropriate.

**Tier 4 - cross-browser/deployed qualification**

- Chromium/Firefox/WebKit compatibility subset;
- immutable deployed startup/save/reload/Continue smoke where package/release rules require it.

### Change classes

At minimum classify changes as:

- **docs-only** - durable-doc/project-contract checks only unless executable config is touched;
- **micro fix** - bounded copy/CSS/local presentation change: Tier 0 + owned targeted tests/build when bundling is affected;
- **bounded feature/subsystem** - Tier 0/1 + owned Tier 2 + build/performance where runtime payload changes;
- **cross-cutting architecture/state/build/test-infrastructure** - escalate to full Tier 3 and relevant Tier 4;
- **WP completion / merge-to-main / release candidate** - always full qualification regardless of selective development history.

### Safety rule

Selective testing is an optimisation for **feedback**, not permission to merge an under-qualified work package. Main/release/final H0 still gets the complete safety net.

### Acceptance

- A 4px/local Settings-style fix no longer needs to spend the same development-cycle CI cost as a repo-wide architecture change.
- A shared/core change automatically escalates.
- CI output states the detected change class and selected test groups.
- There is a manual `full CI` escape hatch.
- A scheduled/periodic full run detects mistakes in the selection map even when no release is pending.

## H0H - Performance architecture and loading policy

### Purpose

Recover durable headroom while measuring what players actually load.

### Required work

- Produce attributable bundle/module reports and before/after deltas.
- Measure title and first-playable dependency graphs rather than only total emitted JS.
- Audit static scene registration and establish deliberate dynamic loading boundaries for optional regions/features.
- Consider lazy boundaries for creator, distant regions, interiors, modal systems, races/minigames and other optional content only where measurement supports them.
- Isolate diagnostics/test-only code from production startup.
- Avoid duplicate shared payloads and tiny-chunk request storms.
- Verify lazy transitions fail/recover sensibly and deployment caching does not leave stale chunk failures unhandled.
- Remove dead/legacy code as proven by H0A/H0J rather than relying on code splitting to hide it.

### Performance policy redesign

During H0, retain visibility of the old 520 KiB entry / 650 KiB total-JS metrics and the inherited WP19H baseline. Do not simply raise 650 KiB.

The reviewed replacement policy must distinguish at least:

1. **initial/entry JS** - hard budget;
2. **title/first-playable dependency graph** - hard budget/target;
3. **largest individual lazy chunk or feature group** - hard budget or explicit reviewed exception;
4. **unexpected duplication/regression** - hard failure when materially worsened;
5. **total emitted JS** - trend/delta evidence for game breadth, not an arbitrary permanent maximum;
6. **startup/first-playable timing** - measured evidence with a stable methodology where CI/device noise permits meaningful thresholds.

Thresholds must come from measured healthy baselines with deliberate headroom. Do not tune limits to the exact current output.

### Acceptance

- H0 ends with comfortable, documented startup/entry headroom rather than a knife-edge pass.
- Optional breadth can grow without automatically increasing initial player cost.
- The new budget report explains what changed and why.

## H0J - Migration and deletion programme

### Purpose

Move the existing game onto the standards rather than leaving new architecture beside old architecture forever.

### Required approach

Migrate in bounded slices with parity evidence. Candidate slices from H0A should include:

- retire `LegacyWorldFeedbackMigrationManager` once all recognised producers use canonical feedback ownership;

- move remaining bespoke message/dialogue/notification surfaces onto canonical owners where behaviour matches;
- remove stale tests, helpers, assets and shims only after replacement/retirement evidence exists;

### Guardrails

- Do not mass-rewrite every scene at once.
- One migration slice should be independently revertible.
- Do not delete a compatibility layer until its callers/producers and regression tests prove it obsolete.
- Preserve positive human-approved visuals/behaviour.

### Acceptance

- The game does not finish H0 with a shiny new design system plus a parallel set of old implementations that future agents still have to choose between.
- Explicit retirement candidates are either removed or have a documented reason/owner/date for remaining.

## CI/test architecture target after H0

The target is **fast feedback during development, full confidence at integration**.

A small local fix should not automatically consume three full browser shards plus every compatibility browser merely because that is the only CI path. Conversely, a selective test result must never be presented as equivalent to final package qualification.

The required CI design therefore has:

- one always-running classifier/static safety job;
- explicit change classification;
- affected unit tests and owned browser groups for PR feedback;
- fail-safe escalation for unknown/shared/core changes;
- a manually triggerable full qualification;
- automatic full qualification for H0 completion, `main` and release candidates;
- periodic full-suite execution to catch classifier blind spots;
- concise evidence showing what was selected and why.

## Explicit non-goals

- No new region, quest pack, minigame or daughter-led R7 feature.
- No visual redesign or new art direction.
- No rewriting stable game rules merely to fit a preferred architecture pattern.
- No save-schema migration unless a separately approved blocker makes it unavoidable.
- No arbitrary performance-budget increase presented as optimisation.
- No deleting valuable regression tests solely to shorten CI.
- No selective-CI system that silently skips unknown risk.
- No framework rewrite away from Phaser/Vite/TypeScript.
- No production deployment before explicit approval.

## Package-level acceptance criteria

H0 is complete only when all of the following are true:

- H0A-H0K deliverables exist and are internally consistent;
- architecture ownership and dependency rules are explicit and mechanically guarded where valuable;
- recurring UI has canonical tokens/components and a supported canvas/DOM overlay contract;
- new-scene construction has a documented, proven composition recipe;
- the existing game has materially migrated onto those standards rather than merely adding abstractions;
- the test suite has a documented user-contract model and known brittle/obsolete tests are repaired or retired with evidence;
- selective CI provides materially faster feedback for micro fixes while failing safe for uncertain/core changes;
- full WP/main/release qualification remains authoritative;
- performance policy protects startup/first-playable and lazy-chunk pathologies without imposing a fixed ceiling on total game breadth;
- there is deliberate performance headroom after H0;
- meaningful proven-obsolete migration/legacy code is removed;
