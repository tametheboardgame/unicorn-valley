H1.11 was deliberately not another visual redesign. The approved Glade appearance and behaviour were the reference. ## Product intent

H1 should leave Moonflower Glade not only looking correct, but structurally trustworthy enough that later work can build on it without rediscovering hidden legacy layers or scene-specific patches.

The target state is:

- one canonical owner for each approved piece of world presentation or interaction;
- obsolete H1-replaced presentation removed at source rather than hidden after creation;
- no polling/scanning workaround whose only purpose is to suppress old presentation;
- shared interaction/dialogue/feedback/pickup patterns reused instead of Glade-only equivalents;
- scene lifecycle cleanup is explicit and leak-safe;
- approved save/quest behaviour remains idempotent and compatible;
- tests describe the final intended architecture/behaviour rather than intermediate H1 checkpoints;
- future region work has a short documented set of reusable implementation conventions.

## H1.11A - Ownership and legacy-suppression audit

Audit all H1.1-H1.10 changed runtime paths and identify code which:

- creates an old object and later destroys/hides/repositions it;
- scans the scene repeatedly to suppress legacy presentation;
- uses delayed cleanup solely because another manager creates a competing object later;
- draws multiple versions of the same path, sign, marker, NPC, feedback surface or environment feature;
- preserves obsolete scene-specific presentation after a shared owner has replaced it;
- contains H1 checkpoint-specific compatibility code that is no longer needed in the final approved state.

Where safe, remove the obsolete source behaviour and delete the compensating cleanup.

The H1.10 Old Garden Gate flower issue is the reference failure mode: the correct fix is removal from `EnvironmentProductionPresentationManager`, not coordinate-based deletion after creation.

## H1.11B - Canonical world-presentation ownership

Confirm and consolidate ownership for at minimum:

- Moonflower Glade paths/routes;
- physical destination signs and legacy entrance labels;
- cottage/garden presentation;
- Moonflower Field and special Moonflowers;
- stream life/reeds;
- Pip/supporting-resident presentation;
- interaction affordances/prompts;
- dialogue cards/portraits;
- transient feedback, guidance and quest completion;
- world collision/occlusion/depth where H1 changed presentation geometry.

There must not be two active systems drawing competing equivalents in the same runtime scene.

## H1.11C - Retire superseded Glade code

Remove or narrow code which is no longer part of the production H1 runtime, including where evidence supports it:

- retired Moonflower Patch scene/entry remnants;
- legacy Glade interaction activation/prompt paths replaced by the shared registry/coordinator;
- obsolete environment/path/sign label drawing;
- unused H1 compatibility constants/helpers;
- stale comments describing superseded proximity collection, separate field scenes or old dialogue presentation;
- dead imports/tests which only protect retired behaviour.

Do not delete compatibility code which still serves another active scene without first proving that dependency.

## H1.11D - Shared pattern standardisation

Promote the approved H1 patterns into clear reusable conventions for later region work:

- physical collectable -> shared explicit `Pick up` interaction;
- ordinary world interaction -> `SceneInteractionRegistry` + shared coordinator/prompt;
- non-dialogue transient feedback -> shared transient ownership/coordinator;
- dialogue -> shared `WorldConversationPresenter` / `DialogueCard` presentation;
- environmental reaction/guidance -> shared `WorldFeedbackPresenter`;
- world presentation objects -> named canonical owner/container where practical;
- map geometry -> semantic map data rather than presentation-time coordinate hunting;
- presentation cleanup -> lifecycle-owned teardown, never perpetual object-list scans;
- physical sign/prop -> visual owner plus semantic collision geometry;
- future feature hooks -> stable semantic ids rather than visual-object references.

Document these rules in a concise repository architecture/conventions note rather than relying on H1 memory.

## H1.11E - Lifecycle and performance hardening

Audit H1 runtime managers for:

- perpetual `POST_STEP`/`POST_UPDATE` work that can be event/state driven or throttled;
- repeated scene-child scans;
- repeated text/icon redraw or rerasterisation;
- duplicate infinite tweens;
- event listeners not removed at game/scene destruction;
- containers/objects surviving scene shutdown unexpectedly;
- state managers that recreate identical objects repeatedly;
- expensive save loads inside high-frequency loops where an existing state/signature can safely avoid them.

Do not optimise by changing approved visual movement or introducing integer-snapped simulation movement.

## H1.11F - Persistence and progression sanity

Review H1-introduced/modified save, discovery, inventory and quest paths for:

- duplicated or obsolete flags;
- double-award/double-completion risks;
- state mutations occurring during presentation selection;
- transient feedback triggering before the state transition it represents;
- save/reload incompatibility with pre-H1 saves;
- hidden dependencies on removed presentation objects.

Preserve the approved H1.9 sequencing: Pip's closing conversation ends before quest-complete feedback appears.

## Audit method

1. Inventory the H1 changed runtime files and identify current owners.
2. Search specifically for suppression smells: child-list scans, delayed cleanup, destroy/hide old objects, compatibility/legacy/H1 temporary naming, duplicate scene-level interaction/UI ownership.
3. Trace each smell back to the source creator before editing.
4. Remove old source behaviour and then remove its compensating workaround.
5. Consolidate only where the approved behaviour is already proven; avoid speculative rewrites.
6. Run focused unit/static/build checks after each bounded consolidation group.
7. Run the full Chromium/WebKit qualification matrix only after the cleanup pass is assembled.
8. Provide a fresh deployed preview for a final Glade parity review before H1 merge approval.
