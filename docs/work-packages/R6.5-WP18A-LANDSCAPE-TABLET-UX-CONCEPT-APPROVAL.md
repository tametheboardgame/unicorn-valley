# R6.5-WP18A - Landscape Tablet UX Concept and Approval

## Objective

Define and obtain explicit human approval for the new **landscape-tablet-first** interface/control direction before doing the expensive shell/control implementation work.

This package is intentionally concept-first. It may create design notes and visual concept images, but it must **not** implement the new gameplay shell, race controls, inventory layout or creator layout in production code.

## Canonical sources

- `docs/07Z-R6.5-WP17-PLAYTEST-REMEDIATION.md`
- `docs/work-packages/R6.5-WP17-FULL-HUMAN-PLAYTHROUGH-R7-READINESS-GATE.md`
- current code for `ExplorationShell`, `ExplorationChrome`, `InteractionPrompt`, `TouchMovementPad`, race touch controls, inventory and creator.

The WP17 human playtest evidence is authoritative over stale assumptions from earlier automated passes.

## Product principle to establish

Unicorn Valley should feel like a game designed to be held and played on a landscape tablet, not a desktop browser game with touch buttons added around it.

The reference human-test device is Samsung Galaxy Tab S8, Chrome, landscape.

Desktop keyboard/mouse remains supported, but concept decisions should first answer: "Is this clear and comfortable for a seven-year-old using a landscape tablet?"

## Required concept set

Create visual concepts for at least the following four surfaces.

### Concept A - Normal exploration shell

Show a representative live exploration scene with enough real world detail to judge occlusion and hierarchy.

Must explore:

- left-thumb movement control position;
- right-thumb Gallop/secondary movement action position;
- large contextual primary action button when an action is available;
- compact Bag, Map, Wonderbook and Settings/Pause access;
- location/title treatment that does not dominate the screen;
- contextual hint/instruction treatment;
- currency/reward feedback placement;
- how the shell behaves when there is no current action;
- enough clear world area that scenery and upcoming destinations remain visible.

The concept should assume tap-to-move remains a first-class option, so the directional pad is not allowed to consume the experience merely because it exists.

### Concept B - Landscape race controls

Show an actual race-like composition with track/obstacles visible.

Must explore:

- controls that do not cover upcoming obstacles;
- RUN/accelerate interaction that cannot depend on a browser long-press gesture;
- jump/dodge/other race actions as applicable;
- thumb reach and multi-touch comfort;
- race progress/position/reward information;
- pause/exit treatment;
- whether a held RUN action remains desirable or should become a safer alternative such as toggle/continuous mode. The concept may compare alternatives rather than assuming the answer.

### Concept C - Bag/inventory and map access

Show how the player opens the bag/map from exploration and what the bag itself looks like.

Must explore:

- Bag and Map as clear distinct actions;
- category/pocket navigation for growing inventories;
- candidate pockets such as Food and Quest Items;
- scrolling item lists;
- large child-readable item cards/rows;
- item use/eat affordance where applicable;
- clear selected-item feedback;
- close/back behaviour;
- no six-item ceiling;
- room for future item categories without redesigning the whole modal.

The visual direction may borrow the organisational principle of category-based inventory systems, but must remain visually original to Unicorn Valley.

### Concept D - Unicorn creator

Show the creator as a landscape-tablet surface.

Must explore:

- large unicorn preview;
- progressive category navigation rather than every option on screen at once;
- candidate sections such as Main, Colours, Mane & Tail, Horn, Markings and Accessories;
- only one option group expanded/active at a time;
- large visual swatches/cards;
- readable naming controls;
- obvious confirm/back/reset behaviour;
- enough space to appreciate the unicorn design rather than surrounding it with controls.

## Optional comparison variants

If a decision is genuinely ambiguous, create two or three meaningfully different variants rather than pretending certainty. Useful comparison points may include:

- D-pad versus compact virtual stick;
- Gallop hold versus toggle;
- bottom-right contextual action button versus central-bottom action button;
- top icon rail versus side icon rail;
- inventory category tabs versus a vertical pocket selector.

Do not create variants merely for decoration. Each variant should test a real interaction/layout decision.

## Visual standard

Concept images should look close enough to a plausible Unicorn Valley screen that the user can assess feel, hierarchy and screen occupation.

Avoid:

- abstract grey wireframes as the only evidence;
- tiny text that cannot be judged at tablet scale;
- fake phone portrait framing;
- excessive permanent panels;
- decorative UI that hides the game world;
- copying another game's branded UI.

## Human review questions

For each concept, the user should be able to answer:

1. Does the world still feel like the main thing on screen?
2. Are the things a child should press unmistakably pressable?
3. Can a left thumb and right thumb reach the important controls naturally?
4. Is there less visual noise than the current shell?
5. Are Bag, Map and other secondary systems easy to find without dominating play?
6. Is the hierarchy understandable without reading desktop-control instructions?
7. Does the visual language still feel like Unicorn Valley?
8. Would the user be happy for this direction to become the implementation authority?

## Deliverables

- approved exploration-shell concept image(s);
- approved race-control concept image(s);
- approved bag/map concept image(s);
- approved creator concept image(s);
- concise design-decision notes recording what was approved and any explicit changes requested by the user;
- links/references to the approved visual assets where practical.

The user has indicated that approved concept images may be reattached in the implementation chat. When supplied there, those approved images are visual authority for WP18C/WP18E unless a later explicit decision supersedes them.

## Hard gate

WP18A is complete only after the user explicitly approves the concept direction.

No landscape-shell/control implementation begins before this approval.

## Exit

On approval:

1. mark WP18A complete;
2. record the approved design decisions durably;
3. move to `R6.5-WP18B - Freeze Diagnostics, Root Cause and Stability`;
4. preserve the approved concepts for WP18C and WP18E implementation.
