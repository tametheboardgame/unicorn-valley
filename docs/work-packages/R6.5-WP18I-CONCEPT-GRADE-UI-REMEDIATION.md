# R6.5-WP18I - Concept-Grade HUD, Button and Text-Box Remediation

## Objective

Replace the still-fragmented tablet HUD/button/text-box presentation with one cohesive, polished game-UI system that follows the user-approved high-fidelity Rainbow Meadow concept as closely as practical within the existing Phaser/TypeScript/Vite game.

This is a **UI-only remediation package**. It must improve layout, styling, hierarchy, readability and contextual presentation without changing world geometry, collision, quest logic, save logic, NPC placement, movement rules, race rules, economy, progression or content.

The 2026-09-07 user-supplied Rainbow Meadow concept is the primary visual authority for this package. The earlier WP18A tablet direction remains structurally compatible, but where the current implementation is visibly more boxy, fragmented or lower quality than the new concept, WP18I should move toward the newer concept.

The concept's Unicorn Valley logo and left-side mini-map are explicitly **not required**.

## Why this remediation exists

The first production check after WP18G showed that the control mechanics are substantially improved, but the surrounding interface still falls short of the approved visual direction:

- top actions remain separate small bordered boxes instead of a single cohesive navigation group;
- location/title presentation is still a plain box rather than a polished status pill;
- status/currency information lacks a clear premium hierarchy;
- contextual actions are not presented as the large, obvious lower-right action button shown in the concept;
- help/hint text is fragmented or placed in small developer-looking boxes instead of a bottom-centre contextual hint pill;
- the lower control area is visually heavy because a large solid backing panel dominates the screen;
- several screens still mix old rectangular controls, raw text boxes and newer tablet controls;
- iconography and button treatment remain inconsistent;
- overlapping HUD elements make the screen feel assembled from separate panels rather than designed as one game UI.

WP18I exists to resolve that gap before another child replay.

## Hard scope boundary

### In scope

- exploration HUD layout;
- top navigation buttons;
- location and status pills;
- currency/progress counters;
- contextual action presentation;
- Gallop button styling and placement;
- directional control styling/backplate only where required for coherence;
- bottom-centre hint/instruction presentation;
- active quest/info cards;
- common button styling across modal/game UI surfaces;
- common text-box/card styling across modal/game UI surfaces;
- iconography used by those controls;
- spacing, layering, touch target, typography and overlap rules;
- responsive behaviour across the established landscape tablet matrix;
- matching race/activity buttons to the same visual family without changing their mechanics.

### Explicitly out of scope

- cottage/window collision or any other world collision change;
- player/NPC/world art changes;
- map/world geometry;
- quest progression or NPC discoverability logic;
- save schema or inventory logic;
- movement speed or controls semantics;
- race mechanics;
- shop logic/economy;
- new content;
- audio logic;
- any R7 feature.

The known cottage collision issue remains a separate unresolved defect and must not be mixed into this UI package.

## Visual authority and target quality

The target should read like a polished child-facing game HUD, not a set of debug panels.

The strongest visual characteristics to reproduce are:

- large rounded controls with generous corner radii;
- cream/ivory surfaces with purple edging and soft lavender shadowing;
- glossy or softly bevelled purple primary buttons;
- gold/orange treatment for Gallop or other secondary action emphasis where appropriate;
- pill-shaped status blocks rather than thin rectangular boxes;
- clear icon + label pairing;
- thick, readable child-friendly labels;
- consistent outline/shadow language across all HUD components;
- deliberate grouping so related controls appear to belong together;
- strong visual separation between navigation, status, movement and contextual action;
- transparent/soft circular control backplates rather than a large opaque lower screen slab;
- high contrast without excessive borders around every individual item;
- minimal clutter in the central play area.

The implementation does not need to reproduce the concept's expensive 3D rendering or background artwork. The required match is the **UI layout, proportions, hierarchy, button language and polish**.

## Detailed layout contract

### 1. Top navigation group

Replace the current scattered top-row boxes with one cohesive grouped navigation surface.

Required actions:

- Map
- Bag
- Book
- Settings

Requirements:

- one shared rounded cream/ivory container or visually joined tab group;
- four evenly sized large touch targets;
- each action uses a purpose-built icon plus readable text label;
- no Sound button as a separate top-level HUD item; sound belongs inside Settings;
- no separate floating Controls/help box when Settings/help already provides that function;
- buttons should have distinct pressed/hover/focus states without turning back into isolated rectangular boxes;
- target sizing must remain comfortable on the Galaxy Tab S8 landscape reference viewport;
- desktop pointer/keyboard behaviour remains supported.

### 2. Top-right status cluster

Create a clean status cluster inspired by the concept.

Required elements:

- Shimmer/currency count using the game's existing authoritative currency;
- star/progress count if an existing authoritative star/progress value is already available and meaningful;
- current location name in a dedicated pill/badge.

Rules:

- do not invent a new currency or progress system solely for the HUD;
- if only one existing counter is truly authoritative, show only that counter rather than fake data;
- status counters should use compact pill surfaces with icon + value;
- location should read as a separate larger rounded pill with a region/location icon where practical;
- remove redundant plain scene-title boxes once the location pill is authoritative.

### 3. Lower-left movement controls

The current movement behaviour is broadly accepted and should not be redesigned mechanically.

Visual remediation:

- keep the four-direction layout;
- retain large touch targets and simultaneous input semantics;
- replace the visually dominant solid lower-screen panel with a compact circular/translucent control backplate similar to the concept;
- use polished purple directional buttons with consistent outline, shadow and pressed states;
- centre spacing should feel intentional and balanced;
- controls must not obstruct the playable centre of the scene.

No change to movement authority, tap-to-move, keyboard movement or input routing.

### 4. Lower-right contextual primary action

Introduce a single large contextual action control in the concept's lower-right action position.

This button should appear only when the player has a meaningful nearby action or current interaction target.

Supported labels should be specific whenever possible, for example:

- Talk
- Enter
- Interact
- Start
- Inspect
- Use
- Buy

Rules:

- prefer the clearest child-facing verb available from the existing interaction authority;
- do not permanently show a disabled generic action button when nothing can be done;
- use one large purple circular/rounded primary button with icon + label;
- the button should be visually stronger than navigation buttons;
- direct NPC tapping and existing keyboard interaction must still route through the same authoritative action path;
- changing visual presentation must not create a second interaction system.

### 5. Gallop button

Retain Gallop as a separate lower-right control beside the contextual action button.

Visual target:

- smaller than the contextual primary action;
- distinct gold/orange treatment inspired by the concept;
- clear unicorn/gallop icon plus text label;
- same tactile outline/shadow quality as the rest of the HUD;
- remains available according to current gameplay rules;
- no change to 1.6x Gallop authority or input behaviour.

### 6. Bottom-centre contextual hint pill

Replace scattered/tiny instruction boxes with one coherent hint surface.

Target:

- rounded cream/ivory pill;
- purple border/shadow language matching the HUD;
- optional small lightbulb/sparkle/icon area;
- one short child-facing instruction at a time;
- anchored bottom-centre between movement and action clusters;
- automatically hidden when no useful hint exists.

Examples of the intended tone:

- Move closer to a unicorn to talk
- Tap Talk to chat
- Walk to the doorway to enter
- Choose a spot to decorate

This is presentation only. Existing hint/interaction state remains authoritative.

### 7. Quest/info card

Where the game needs to show an active current quest or immediate objective, use a compact polished card inspired by the concept rather than tiny floating text.

Requirements:

- optional/conditional, not permanently visible without useful content;
- cream/ivory surface with icon, concise heading and one objective line;
- rounded corners, purple edging and soft shadow;
- positioned so it does not overlap the top nav, movement pad, contextual action or bottom hint;
- may occupy the upper-left/left-middle space because the concept mini-map is intentionally omitted;
- should collapse or disappear when there is no active objective.

### 8. Common button component system

Create or consolidate a reusable shared button visual system rather than styling each scene independently.

At minimum define reusable variants for:

- navigation/tab button;
- primary action button;
- secondary/gold action button;
- modal confirm button;
- modal cancel/back button;
- compact icon button;
- disabled state;
- selected/active state.

Each variant must define:

- geometry/radius;
- fill treatment;
- outline treatment;
- shadow/depth treatment;
- icon sizing;
- label typography;
- pressed state;
- hover/focus state for desktop;
- minimum touch target;
- reduced-motion-safe feedback.

Avoid browser emoji as the primary visual icon language where a small purpose-built vector/drawn icon can be used without bloating the application bundle.

### 9. Common text-box/card system

Create or consolidate shared visual treatments for child-facing text surfaces.

Required variants:

- hint pill;
- location/status pill;
- quest/info card;
- dialogue/action prompt card where appropriate;
- modal panel/card;
- small notification/toast/reward card.

Requirements:

- consistent cream/ivory/purple visual language;
- readable padding and line height;
- no tiny text solely to make content fit;
- text should wrap cleanly rather than overflow;
- decorative borders must not overwhelm the text;
- use clear hierarchy between title, body and metadata;
- avoid multiple adjacent boxes for information that can be grouped into one surface.

### 10. Modal/screen button and text-box reconciliation

Without redesigning the underlying Bag, Map, Creator, Settings or other modal flows, bring their visible controls into the same design family.

This includes:

- primary and secondary action buttons;
- tab/category controls;
- close/back controls;
- selected states;
- information cards;
- item/detail panels where they still use raw rectangular presentation.

The purpose is visual consistency, not new layout architecture or new functionality.

### 11. Race/activity visual reconciliation

Do not change race RUN/JUMP semantics or positions already validated by WP18G.

Restyle the race/activity controls so they belong to the same UI family:

- RUN and JUMP use polished large action-button styling;
- no steering controls are introduced;
- central track corridor remains unobstructed;
- simultaneous RUN + JUMP remains intact;
- long-press suppression remains intact;
- pause/assistance controls retain current function while receiving the shared UI treatment where practical.

## Layout hierarchy rules

The screen should always read in this order:

1. game world;
2. contextual primary action;
3. movement controls;
4. navigation/status;
5. supporting hint/quest information.

No HUD element may create the current impression of many equally important boxes competing for attention.

Additional rules:

- central gameplay space should remain visually open;
- left and right control clusters should feel balanced;
- no persistent full-width or near-full-width opaque lower panel;
- avoid duplicate location/help/sound/control information;
- HUD groups may overlap scenery but must not overlap each other;
- safe margins must account for browser chrome/device edges;
- interaction controls should remain within comfortable thumb zones on landscape tablets.

## Responsive/device contract

Primary reference:

- Samsung Galaxy Tab S8, Chrome, landscape.

Automated visual/layout checks should retain WP18G coverage for:

- 1280x720 16:9 landscape;
- 1280x800 16:10 landscape/reference style;
- 1024x768 4:3 landscape;
- 960x600 smaller landscape tablet;
- 1600x1000 larger landscape tablet;
- 1280x720 desktop with touch disabled.

For narrower layouts:

- reduce gaps before reducing button target size;
- allow grouped nav/status clusters to compact intelligently;
- preserve readable labels;
- never reintroduce overlapping independent boxes;
- do not scale primary touch targets below the established accessibility floor.

## Implementation approach

### Phase I.1 - UI inventory and consolidation

- enumerate every exploration HUD button/text box currently rendered;
- identify duplicate/obsolete controls such as separate Sound/Controls boxes;
- identify existing shared UI utilities that can be extended instead of creating per-scene copies;
- record authoritative data sources for Map, Bag, Book, Settings, location, Shimmer, optional star/progress, quest and contextual action.

### Phase I.2 - Shared visual primitives

- build reusable surface/button/card primitives;
- establish consistent radius, border, shadow, spacing and typography tokens;
- create lightweight purpose-built icons where existing icon quality is insufficient;
- keep the hard 520 KiB application-entry budget unchanged.

### Phase I.3 - Exploration HUD replacement

- replace scattered top controls with grouped Map/Bag/Book/Settings navigation;
- add status/currency/location pills;
- remove redundant Sound, Controls and duplicate title boxes;
- restyle movement backplate/buttons without changing movement behaviour;
- remove the large opaque lower deck where the new compact control composition makes it unnecessary.

### Phase I.4 - Contextual action and hint system presentation

- bind the existing authoritative interaction state to one lower-right primary action control;
- dynamically label/icon the control by action type;
- show/hide it contextually;
- add the bottom-centre hint pill using existing hint state;
- verify direct-tap and keyboard interaction paths remain unchanged.

### Phase I.5 - Quest and information surfaces

- move active objective copy into a polished optional quest/info card;
- consolidate reward/status notifications into the same visual language;
- eliminate tiny floating developer-style text where a proper card/pill is appropriate.

### Phase I.6 - Modal and activity reconciliation

- apply shared button/card language to Bag, Map, Book, Creator, Settings and major modal surfaces without changing their logic;
- apply the shared action language to race/activity controls without altering mechanics.

### Phase I.7 - Overlap, device and visual evidence pass

- run the established viewport matrix;
- check all shell groups for overlap and safe-area containment;
- capture visual evidence for normal exploration, nearby NPC, doorway/enter action, decoration mode, Bag, Map, Settings/Creator and at least one race;
- compare visual hierarchy directly against the concept target rather than only checking that controls technically fit.

## Acceptance criteria

WP18I is ready for its human visual gate only when all of the following are true:

### Concept fidelity

- top Map/Bag/Book/Settings controls read as one polished navigation group;
- location/status counters read as designed pills rather than plain boxes;
- contextual action appears in the lower-right concept position only when relevant;
- Gallop is a distinct polished secondary action beside it;
- bottom-centre hint pill is present when useful;
- movement controls use a compact polished backplate rather than a dominant solid lower deck;
- common buttons/text boxes visibly share one premium visual language;
- the overall screen resembles the concept's UI hierarchy even though the logo and mini-map are omitted.

### Clarity

- no duplicate top-level Sound/Controls boxes;
- no overlapping HUD groups on the reference landscape tablet;
- no tiny unreadable instruction boxes;
- central gameplay view remains clear;
- child-facing verbs are explicit and context-specific;
- location, currency and quest information are immediately distinguishable from actions.

### Behaviour preservation

- Map, Bag, Book and Settings still open the same authoritative surfaces;
- tap-to-move, directional movement and Gallop work exactly as before;
- direct NPC tap and keyboard interaction still work;
- contextual button invokes the existing interaction authority rather than a duplicate system;
- race RUN/JUMP behaviour is unchanged;
- save/progression state is untouched.

### Technical

- project contract green;
- formatting/lint/type-check green;
- unit tests green;
- production build/static smoke green;
- hard 520 KiB application-entry budget remains unchanged and green;
- Chromium/Firefox/WebKit compatibility green;
- full serial Chromium playtest green;
- dedicated WP18I visual/layout tests cover the required viewport matrix and interaction states.

## Human visual gate

A visual spot-check is required before WP18I is considered complete.

The evidence set should include at minimum:

1. normal landscape exploration with no nearby interaction;
2. exploration beside an NPC showing Talk;
3. exploration beside a door/gateway showing Enter/Interact;
4. decoration mode;
5. Bag or other major modal showing reconciled button/card styling;
6. a race showing the shared visual family while preserving RUN/JUMP placement;
7. at least one 4:3 or smaller-landscape screenshot proving the layout compacts cleanly.

The review question is not merely “does it fit?”. It is: **does this now look and feel like the high-quality concept UI rather than a collection of separate boxes?**

Material visual drift from the concept requires user review rather than silent substitution.
