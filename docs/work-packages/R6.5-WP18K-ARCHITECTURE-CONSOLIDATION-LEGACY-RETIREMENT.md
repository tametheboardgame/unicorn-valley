# R6.5-WP18K - Architecture Consolidation and Legacy Retirement

## Objective

Perform a repo-wide, behaviour-preserving architecture audit and cleanup after the accepted WP18I/J UI remediation. Remove obsolete generations of presentation code and consolidate the surviving implementation into clear canonical owners so future work does not continue accumulating patch-on-patch managers.

This package is intentionally suited to ChatGPT **Work mode** because it requires broad repository inspection, dependency tracing, repeated validation and coordinated refactoring rather than another narrow visual patch.

## Starting baseline

Canonical production baseline: `d8f3de6f264fa5fd6e2d77d539a47f288eb50cd4`.

Canonical UI acceptance:

- concept shell approved across desktop/laptop, tablet landscape, phone landscape and phone portrait;
- static HUD overlay fixes camera-follow jitter;
- Bag/Map/Wonderbook final presentation approved;
- map panning/clipping final presentation approved;
- no Bag Shop teleport shortcut;
- old landscape fallback is retired.

Human feedback authority: `docs/HUMAN-PLAYTEST-FEEDBACK-LEDGER.md` and `docs/07Z-R6.5-WP17-PLAYTEST-REMEDIATION.md`.

## Required audit before deletion

Work must inventory and trace ownership/dependencies for:

- scene registration and dynamic imports in `src/main.ts`;
- exploration shell/chrome/HUD rendering;
- responsive presentation detection and portrait/landscape managers;
- modal presentation and reconciliation layers;
- old R5/R6/R6.5 visual managers and cleanup managers;
- touch/race control presentation layers;
- scene-specific temporary polish managers;
- CSS files and selectors no longer reachable from canonical UI;
- tests that assert retired UI rather than current product behaviour;
- dead assets, unused helpers, duplicate constants/tokens and diagnostic-only production paths.

Known candidates that require evidence rather than automatic deletion include `DesktopConceptPresentationManager`, `DesktopConceptCleanupManager`, `ModalConceptPresentationManager`, `Wp18jResponsiveUiPolishManager`, `Wp18jMapViewportClipManager`, `UiProductionPresentationManager`, `ExplorationShell`, `ExplorationChrome`, `ExplorationHudOverlayScene` and overlapping responsive helpers. Some are canonical, some transitional and some likely obsolete. Trace before changing.

## Work phases

### K1 - Architecture map

- enumerate active scenes/managers and who creates them;
- build a dependency/ownership map for UI and responsive behaviour;
- identify canonical implementation, compatibility shim, temporary remediation and dead code;
- record deletions/consolidations proposed before executing high-risk removals.

### K2 - Legacy retirement

- delete genuinely unreachable or retired UI paths;
- remove obsolete alternate layouts rather than leaving hidden resurrection paths;
- remove stale code/assets/tests whose only purpose is the old product;
- update current-behaviour tests instead of restoring old runtime objects.

### K3 - Ownership consolidation

- move stable WP18I/J behaviour into the most appropriate scene/component owner;
- reduce global POST_STEP reconciliation where normal scene lifecycle/state ownership can replace it safely;
- collapse duplicate visual tokens/primitives;
- simplify responsive authority so each display class has one deliberate path;
- simplify `src/main.ts` bootstrapping and scene registration where safe.

### K4 - Test and diagnostic cleanup

- retain regressions for every human-observed failure mode that remains relevant;
- remove/update tests that assert deleted legacy UI;
- keep freeze, save, progression, interaction, race, Bag/Map/Wonderbook and responsive coverage;
- keep useful diagnostics without shipping unnecessary production-only debug layers.

### K5 - Full validation and evidence

- format, lint, type-check and unit tests;
- production build/static smoke;
- hard 520 KiB entry budget;
- Chromium/Firefox/WebKit compatibility;
- full serial Chromium playtest;
- screenshots/geometry checks for all four responsive display classes;
- repeated modal open/close and map-drag checks;
- save/continue smoke where existing automation supports it.

## Hard behaviour guardrails

WP18K must **not** intentionally change:

- save schema or compatibility;
- quest/progression logic;
- map topology or route data;
- inventory/item semantics;
- economy/reward rules;
- NPC authoritative state;
- player movement authority, Gallop multiplier or tap-to-move semantics;
- race mechanics or RUN/JUMP semantics;
- world geometry/collision;
- content, dialogue or unlocks;
- the approved visual design.

If cleanup reveals a genuine functional defect, record it and either fix it in a separately bounded defect commit/package or stop for user direction if it changes product behaviour materially.

## Known out-of-scope defect

Moonflower Cottage/window/back-wall collision is already known and remains unresolved. Do not claim WP18K fixed it unless a separately bounded collision remediation is explicitly performed and tested.

## Acceptance criteria

WP18K is complete only when:

- there is a documented architecture/ownership map;
- obsolete UI generations and dead code are actually removed, not merely hidden;
- canonical responsive/UI behaviour has clear ownership and fewer reconciliation layers;
- no known accepted UI behaviour regresses;
- human feedback and preservation requirements remain represented in tests/docs;
- the 520 KiB budget remains unchanged;
- core, browser compatibility and full browser playtest evidence is reviewed;
- `ROADMAP.md`, `STATUS.md` and `PROJECT_STATE.json` are updated to the post-cleanup truth;
- delegated manager review confirms the four-class evidence did not alter the accepted product presentation; this does not claim physical human/device acceptance.
