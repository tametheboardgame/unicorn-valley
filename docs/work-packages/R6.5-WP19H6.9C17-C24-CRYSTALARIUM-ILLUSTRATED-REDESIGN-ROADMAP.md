# H6.9C17–C24 — approved Crystalarium illustrated UX rebuild

**Human approval, 28 October 2026:** user confirmed the **illustrated, blue-purple garden concept including the background**, board-first composition, larger crystal wells, rounded controls, distinct Storage Chamber, focused illustrated spotlight tutorial, reduced text and glowing recipe card as direct Offer action. New explicit requirements: **multiple simultaneous active orders**, scroll horizontally across the order cards, and use a visible **Growth Potion** liquid reservoir (much larger than ten) and droplet-to-well growth animation **instead of energy**.

**Baseline:** latest verified draft technical qualification [CI #40687822730](https://github.com/tametheboardgame/unicorn-valley/actions/runs/40687822730) on `91d29e95` passed Tier 0, targeted **22/22 Crystalarium Chromium** cases, build/performance, draft Merge Gate and SHA-bound [Cloudflare preview](https://f4cd699b.unicorn-valley.pages.dev). The user approved a new concept, **not the revised playable build**, and there is no merge authorisation.

**Canonical design:** [28 October illustrated art and interaction contract](../design/2026-10-28-CRYSTALARIUM-APPROVED-VISUAL-AND-INTERACTION-CONTRACT.md).

## Supersession and non-negotiable constraints

- This roadmap **supersedes the presentation/economy proposals** in C11–C16 where they conflict: **remove** the separate Growing section, permanent shelf strip and standalone Offer button; make order cards themselves tappable Offer targets; use image-led rounded UI and real spotlight guide; implement horizontally scrolled multiple active order cards; represent any consumed growth resource as **Growth Potion**, *not* Crystal Energy. The earlier C13B separate producer-charge counter is **deferred/rejected as a default**: no dual-resource system.
- Keep C11B's actual allowed-action controller tutorial, C13A's three rooted 0/4/7-unlocked wells **outside all 42 sockets**, equal-family equal-tier merge rule, 18 crystal appearances/six tiers, 50 authored orders/five chapters, non-destructive Brook Wash, optional Harmony/Polish, H6.9B Grotto opening melody, in-cave quest and both entry points.
- Retain the **no-hard-wait** child-first promise: 50 orders must be achievable from empty/dry resource conditions without real-world time gating, payment, daily events or mandatory adventure world rewards. Offline/old-save/Just Games players must not be stranded by potion, full board or full storage. The new resource can pace the interface but must never remove a reliable free continuation.
- Do not change original Grotto unlocking, move established quests, fork the crystalarium engine, modify independent MG/Pond Leap PR #289, or edit root `STATUS.md` / `PROJECT_STATE.json` on World draft branch. Do not merge until user visual approval and authoritative H6.9D checks.

### C18 — multi-order queue pure rules and migration (architecture/data gate B)

**Deliverables:** evolve the single `completed` cursor to stable authored pattern IDs with completed-ID ledger and active queue/reveal cursor. Maintain exactly **50** total offers, chapter unlocks and finished/free-play behaviour. **Candidate display progression:** 1 active during first lesson, 2 after first completion, 3 after first chapter; possibly 4–5 later following readability playtest. Only revealed active orders are visible; horizontally scroll without changing board space.

Players can collect crystals towards **all visible orders concurrently**. Each card computes requirements (including harmonies and inventory/storage). Clicking **any ready** card atomically consumes precisely that order's requirements; recompute other card readiness immediately, prevent double consumption and wrong-order progression. Completing one reveals the next eligible uncompleted authored order without shuffling existing open cards. Total progress drives the existing 0/4/7 well unlocks and chapter restoration; retain expected source isolation.

**Migration:** map legacy `completed=N` into the first N finished IDs; preserve every saved board item, four shelf items, harmony and other counters; version the full-state schema in both adventure and sandbox stores with backward compatibility, corruption/future-version fail-safe rules. Define whether `completed` stays as derived compatibility field or is replaced only after audits of all callers. No schema write before reviewed design.

**Tests:** 50-order solver with nonsequential order selection, two overlapping ready cards using the same crystal, independent ready state and one atomic consumption, queue advancement and scroll stability, 0/4/7 unlock behaviour, legacy N=0/N=49/N=50, migration idempotency, reload/corrupt records, separate adventure/Just Games saves and original Grotto gate. **Gate B:** review save/queue model before destructive-looking migration changes; preserve existing save records and exact test evidence.

### C20 — Growth Potion reservoir, balance and droplet interaction (economic gate D)

**Approved vocabulary and look:** **Growth Potion** (not "energy"; treat old "Growth Fluid" as the same concept, not an additional resource), tall/clear gauge above the board-attached wells, fluid/drop animation, animated crystal emergence, source-specific crystal art and clear remaining stock. Do **not** implement these as fixed rules or migrate saves until user approval of the actual cost/refill design. Avoid the previous dual "advanced charges + potion" approach.

Invalid/full/tutorial-rejected actions consume zero, and failure to save never reports a spend. Caps, refunds, rewards and cross-source isolation are deterministic and idempotent. Do not add wider-Valley potion rewards without a **separate explicit grant approval**.

**Tests:** exhausted bottle / full board / no legal move, free recovery then legal growth, 50-pattern solver from dry state, cost affordability/refund/overflow, merge/offer rewards, reload/migration/source isolation, repeated-click prevention, focus/drag, muted/reduced-motion, no timer. **Gate D:** approve actual reservoir capacity, refill method, crystal costs and progression pacing after 5/15/45-minute comparative playtests. **Do not code the new resource counter before this gate.**
