# R6.5-WP18C - Landscape Tablet Controls and Interaction Shell

## Objective

Implement the human-approved WP18A landscape-tablet shell and control direction as a shared system, replacing the current pattern where portrait touch receives special treatment while landscape tablets mostly inherit desktop/canvas chrome.

## Design authority

- Approved WP18A concept images and recorded decisions.
- `docs/07Z-R6.5-WP17-PLAYTEST-REMEDIATION.md`.
- Samsung Galaxy Tab S8, Chrome, landscape as the reference human-test environment.

If code convenience conflicts with the approved concept, preserve the approved interaction intent unless a technical limitation is documented and the user approves a deviation.

## Core implementation requirements

### Tablet-mode detection

Create a coherent tablet/touch presentation decision that does not equate "mobile" with narrow portrait width.

Use appropriate signals such as coarse/touch pointers, orientation and effective viewport/aspect constraints. Avoid brittle device-model user-agent rules.

### Exploration controls

- Preserve tap-to-move as a first-class movement method.
- Keep directional movement available without letting it dominate the screen.
- Place touch controls in comfortable landscape thumb zones according to the approved concept.
- Rework Gallop according to the approved hold/toggle/placement decision.
- Support simultaneous movement/action input safely where the chosen control design requires it.
- Prevent stuck axes/buttons after pointer cancel, pointer leave, scene pause, modal launch or focus loss.

### Contextual primary action

Provide one unmistakable large contextual action surface when an action is available, e.g. Talk to Pip, Enter Shop, Pick Up, Examine or Start Race.

- The label must state the actual action.
- Direct tapping of an eligible NPC/interactable should also work where spatially sensible.
- Direct tap and contextual action must invoke the same authoritative interaction path, not duplicate bespoke logic.
- Automatic gateways/transitions remain automatic only where that is deliberately designed.

### Permanent shell/chrome

Implement the approved compact treatment for:

- Bag;
- Map;
- Wonderbook;
- Settings/Pause;
- location identity;
- currency/reward feedback;
- contextual hints.

Remove or collapse desktop-oriented permanent help chrome that contributes to clutter.

### Device-appropriate help

Child-facing help must describe the controls present on the current device.

On landscape tablet do not lead with WASD/keyboard instructions. Desktop may still show keyboard guidance when appropriate.

### Layout safety

Create shared layout/safe-zone rules so shell components do not overlap each other or critical gameplay.

- No silent text clipping.
- Text wraps, truncates deliberately with a usable affordance, or scrolls.
- Primary touch targets are generous and consistent.
- The gameplay world remains the dominant visual surface.

## Race-control integration boundary

WP18C establishes the common tablet interaction/control primitives and applies the approved race-control treatment where shared infrastructure is required. Race-specific gameplay regressions remain eligible for WP18D.

The known Galaxy Tab S8 long-press problem must not survive: no required race action may depend on a browser gesture that Chrome can interpret as navigation/context long-press behaviour.

## Regression coverage

Add browser tests that exercise the real tablet-facing flows, including:

- landscape coarse-pointer shell selection;
- tap-to-move;
- directional control press/release;
- Gallop according to approved behaviour;
- simultaneous/multi-touch paths where supported by automation;
- contextual action visibility and activation;
- direct NPC tap and contextual button reaching the same action;
- modal launch/pause/resume without stuck input;
- no overlap between major shell controls and the configured gameplay-safe area;
- device-appropriate help copy.

## Preserve

- desktop keyboard/mouse support;
- existing save/progression authority;
- strong point-and-click behaviour;
- 520 KiB application-entry budget;
- browser compatibility suite.

## Acceptance

WP18C is complete when the approved shell exists as reusable production infrastructure, normal exploration is comfortable on landscape tablet, contextual actions are obvious and consistent, race touch input no longer suffers the known browser long-press blocker, and automated tablet/desktop regressions remain green.
