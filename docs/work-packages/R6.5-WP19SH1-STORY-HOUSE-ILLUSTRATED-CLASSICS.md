# R6.5-WP19SH1 - Story House Illustrated Classics Programme

## Purpose

Create a separate, repeatable content stream for reillustrating selected Story House classics with
new ChatGPT-generated artwork and materialising those images through the permanent R4 generated
asset pipeline.

This programme is intentionally independent from the main area/interior polish stream. Once R4 is
merged and accepted, SH1 may proceed concurrently with H3.11.5 Rosehip Cottage and later world
work because the normal SH1 change surface is confined to Story House content, generated-asset
manifests and Story House documentation.

The default content path is:

**select existing Story House text → define visual brief → generate image(s) in ChatGPT → stage in
Google Drive → R4 GitHub Actions materialisation → wire generated WebP to stable reader block IDs →
Cloudflare visual review → merge**

SH1 does not require the main game-development stream to stop.

## Concurrency contract

SH1 is parallel-safe with the world/interior stream when a title changes only:

- `public/stories/<story-id>/**`;
- `generated-assets/manifests/story-*.json`;
- Story House-specific content documentation;
- `public/stories/catalogue.json`, regenerated from story manifests.

Normal SH1 title work must not modify:

- exploration/world maps;
- NPC movement or dialogue systems;
- player movement/input;
- shop/interior gameplay;
- general UI outside Story House;
- save architecture;
- shared performance infrastructure.

If a title exposes a genuine Story House reader defect, isolate that runtime correction in its own
small foundation/remediation PR before continuing art production. Do not mix a broad reader rewrite
into an illustration-content PR.

Only one SH1 title/batch PR should update `catalogue.json` at a time. SH1 can run concurrently with
the main game stream, but multiple overlapping Story House catalogue PRs should be avoided unless
there is a specific reason.

## Illustration/provenance rules

Generated illustrations are new Story House assets, not replacements for public-domain source
files at repository level.

- Generated assets live under
  `public/stories/<story-id>/illustrations/generated/`.
- Historic/public-domain/source images remain in their existing source folders.
- Story manifests must describe generated-image provenance separately from historic illustration
  provenance.
- Public-domain text status and generated-image rights/provenance are separate metadata concerns.
- Every reader image attaches to a stable `blockId`; never use line numbers or character offsets.
- Generated images should be materialised through R4 rather than uploaded directly through the
  GitHub connector.
- Each title gets human visual review in Cloudflare before merge.

## Visual continuity contract

Before generating a multi-image title, establish a small title-specific visual bible containing:

- character appearance and distinguishing features;
- age/scale relationships;
- clothing/accessories that must remain stable;
- key location palette/materials;
- intended illustration medium/style;
- aspect ratio and reader framing;
- recurring props;
- elements that may deliberately change across the story.

For recurring characters, approve a small anchor set before generating the full book. Do not
generate twenty unrelated images and attempt to repair continuity afterwards.

The visual bible is content guidance, not a requirement to train/fine-tune a model.

## Checkpoint sequence

### SH1.1 - Generated classics foundation and content audit

- Adopt the R4 generated-asset pipeline and Story House runbook as the only normal generated-image
  transfer route.
- Record the current title/illustration audit in this roadmap.
- Define generated illustration naming, provenance and `illustrations/generated` storage rules.
- Confirm title work is parallel-safe with the world/interior stream under the concurrency contract.
- Keep historic/source illustrations intact.

**Acceptance:** the content stream can start a title without inventing new binary-transfer,
provenance or repository-layout rules.

### SH1.2 - Pilot: The Lion and the Mouse

Use the smallest clean classic as the first production generated-art pilot because it currently
has no cover or reader illustrations.

Target:

- generate one cover;
- generate approximately 3 story illustrations tied to stable blocks;
- establish a reusable character look for Lion and Mouse;
- materialise every generated asset through R4;
- update rights/provenance metadata;
- regenerate the Story House catalogue;
- validate desktop/tablet/phone reader presentation and lazy loading;
- visually approve the deployed title.

Do not change the prose unless a genuine content defect is separately identified.

**Acceptance:** a currently text-only classic becomes a coherent illustrated Story House title
using only the permanent generated-art workflow.

### SH1.3 - Quick-read classics batch

Process short titles individually, using one PR/title unless a very small pair is explicitly
approved:

1. The Hare and the Tortoise
2. The Town Mouse and the Country Mouse
3. The Elves and the Shoemaker
4. The Princess and the Pea

Primary purpose is to prove repeatable character consistency, location contrast, costume continuity
and fast replacement iteration across several small books without touching reader runtime.

**Acceptance per title:** approved generated set is materialised through R4, correctly anchored,
provenance-correct, responsive in the reader and merged independently.

### SH1.4 - Mid-length fairy-tale batch

Proceed title-by-title:

1. Snow-White and Rose-Red
2. The Twelve Dancing Princesses
3. The Ugly Duckling
4. Thumbelina

These titles deliberately increase continuity difficulty:

- recurring sibling/animal characters;
- repeated costumes and ensemble scenes;
- transformation across seasons/time;
- miniature fantasy scale and recurring locations.

**Acceptance per title:** visual bible holds across the full book and no title requires reader
architecture changes merely to accommodate its artwork.

### SH1.5 - Long-form classic retellings

Proceed title-by-title:

1. The Wonderful Wizard of Oz
2. Five Children and It
3. The Princess and the Goblin

For long-form titles, generate in bounded chapter/scene batches rather than one huge art run.
Approve representative character/location anchors first, then expand.

Keep demand loading intact and avoid excessive image density. Generated art should support reading,
not turn every paragraph into a full-page asset.

### SH1.6 - Dual-edition generated reillustration

Review the three existing dual-edition books after the generated-art workflow is mature:

1. Alice's Adventures in Wonderland
2. The Tale of Peter Rabbit
3. The Tale of Jemima Puddle-Duck

Rules:

- preserve Peter Rabbit's 26 and Jemima's 25 historic full-classic illustrations unchanged;
- preserve historic/source Alice artwork;
- generated art should normally enrich/reillustrate the Story House edition rather than erase the
  Full Classic source-art experience;
- if a distinct visual edition becomes desirable, first determine whether the current edition
  schema can express it cleanly without a broad reader rewrite;
- do not duplicate complete text solely to work around an illustration-set limitation unless the
  trade-off is explicitly approved.

Alice is the strongest later stress test because the full classic already spans 71 reader pages.

### SH1.7 - Classics programme consolidation

After a useful set of titles has been accepted:

- audit generated manifests and Drive staging residue;
- remove obsolete staging files/manifests that are no longer needed for iteration;
- verify generated assets remain separated from historic/source artwork;
- verify rights/provenance metadata across completed titles;
- run Story House catalogue/unit/browser regressions;
- document any stable art-direction conventions worth reusing;
- confirm the generated pipeline still supports in-place replacement without credentials or manual
  binary upload.

SH1 remains open-ended after consolidation if David chooses more classics. New titles should be
added as bounded SH1.x slices rather than forcing an arbitrary fixed endpoint.

## Per-title delivery loop

Each illustrated classic follows this small reviewable loop:

1. select title and confirm illustration scope;
2. produce/approve the visual bible or anchor images;
3. generate one bounded image batch;
4. stage images in Drive;
5. add/update R4 manifests;
6. let Actions materialise WebPs into the title branch;
7. wire assets to stable Story House blocks;
8. run focused catalogue/reader validation;
9. deploy Cloudflare preview;
10. human visual review;
11. iterate via same-Drive-file replacement where needed;
12. merge the title only after approval.

This loop is deliberately independent of H3.11.5+ world development.
