# R6-WP6.17 — Front-End Resilience and Cosmetic Pipeline Hardening

## Purpose

WP6.17 consolidates the resilience guarantees added across R6 before the mandatory human playthrough gate in WP6.18. The audit found that the production save, settings and creator code already contains the required fallback behaviour, so this package strengthens regression coverage and documents the maintenance contract rather than introducing unnecessary runtime changes.

## Loading-state and asset audit

- `PreloadScene` provides an explicit, deterministic loading state before the requested front-door or diagnostic scene starts.
- The R6 menu, dialogue and creator polish is primarily Phaser vector/text presentation, DOM controls and Web Audio. It does not introduce new external network dependencies that can block startup.
- Core NPC production presentation is loaded as deferred presentation code, keeping optional visual work out of the initial entry path.
- The WP6.16 creator delight layer is procedural presentation. It does not require new raster, font or audio downloads.
- New front-end polish must not make startup, Continue, Settings or the creator depend on an optional cosmetic asset being present.

## Browser resilience contract

Automated browser coverage now verifies the following together:

1. A structurally corrupted primary profile can recover from the last-known-good backup and Continue remains usable.
2. Malformed audio and accessibility settings fall back to safe defaults.
3. Invalid optional cosmetic IDs fall back to supported defaults and cannot block My Unicorn or Continue.
4. Returning-player routes remain usable: Continue, My Unicorn and Settings.
5. New-player routing remains usable: Settings, then New Game into the creator.
6. The resilience path produces no browser console errors or failed network requests.

These tests complement the earlier R6 save-recovery, profile-redesign, settings and deployment suites rather than replacing them.

## Cosmetic registry contract

`UNICORN_COSMETIC_REGISTRY` remains the source of truth for creator choices. Future cosmetic additions must follow these rules:

- IDs are stable, lower-case identifiers. Prefer lower-case kebab-case when a name needs more than one word.
- IDs already stored in saves must not be renamed or repurposed casually.
- Every category must retain a valid default ID from `DEFAULT_UNICORN_APPEARANCE`.
- Every choice must have a non-empty ID and player-facing label.
- Duplicate IDs within a category are invalid.
- Every registered choice must survive `parseUnicornAppearance()` unchanged.
- Registered categories are assumed to be freely combinable. Pairwise registry tests enforce that assumption.
- If a genuine incompatibility is introduced later, represent it explicitly as data with tests. Do not hide compatibility rules inside creator input handlers or scene-specific branches.
- Unknown or removed optional IDs must degrade to the category default rather than making the profile unloadable.

## Future cosmetic asset convention

The current creator does not require per-cosmetic external files. If external cosmetic assets are introduced later, keep them under one predictable root, for example:

`public/assets/unicorn/cosmetics/<category>/<cosmetic-id>/`

The registry should continue to identify the cosmetic and its presentation metadata. Do not scatter one-off asset imports or special-case IDs through scenes. Asset absence must have a safe visual fallback where the cosmetic is optional.

## UI and presentation conventions

- Shared palette, typography, button and shadow behaviour belongs in `src/game/ui/uiTheme.ts` or another clearly shared UI primitive.
- Reusable cross-scene or presentation-only polish belongs under `src/game/visual` as a manager or shared presenter where appropriate.
- `UnicornCreatorScene` owns creator interaction and state flow; profile persistence remains in save/profile services.
- Presentation managers must not mutate quests, progression, inventory, relationships or player profile data.
- New menu or creator effects must respect Reduced Motion when motion is not required for gameplay.
- New sound feedback must use the existing settings-controlled audio system rather than bypassing mute/music/ambience/SFX preferences.

## Test coverage added in WP6.17

### Unit-level registry audit

`src/game/player/UnicornAppearance.test.ts` now verifies:

- every registered category contains its configured default;
- every registered cosmetic ID is accepted by the parser;
- every registered cross-category pair remains parser-compatible.

### Browser-level resilience audit

`tests/play/r6-wp6.17-resilience-pipeline.spec.ts` verifies:

- structural profile corruption recovery from backup;
- malformed settings fallback;
- invalid optional cosmetic fallback;
- Continue, New Game, My Unicorn and Settings routing;
- no console errors or failed requests through the tested resilience path.

## Boundary

WP6.17 does not change save schema, progression, story, quests, economy, racing, movement or creator content. Production runtime code should only be changed if the hardening tests expose an actual defect.

## Exit condition

WP6.17 is complete when formatting, lint, TypeScript, unit tests, production build/performance budgets, static smoke, browser regression, cross-browser compatibility, Cloudflare preview and review findings are green. The project must then stop at WP6.18 for the full human playthrough before any R7 work begins.
