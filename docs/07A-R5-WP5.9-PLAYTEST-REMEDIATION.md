# R5-WP5.9 - Exploration Playtest Remediation Roadmap

Status: **Approved for autonomous implementation**

Parent work package: `R5-WP5.9 - Exploration Playtest and Content Density Pass` in `docs/07-WORK-PACKAGES.md`.

This document is the authoritative expansion of R5-WP5.9 following the manual playtest performed after R5-WP5.8. It preserves the original WP5.9 purpose, but splits the remediation into bounded sub-packages so implementation can proceed safely and autonomously without losing the player-observed context.

R6 must not begin until R5-WP5.9A through R5-WP5.9G are complete and the resulting R5 build has passed a final playtest/release gate.

---

## Why WP5.9 is now a consolidation phase

The playtest identified a structural consistency problem rather than a collection of isolated defects.

The older exploration areas currently use the established HUD, keyboard interactions, hint system and transition conventions, while Crystal Brook, Whispering Woods and several newer systems have started to implement their own controls, overlays and interaction paths. Continuing to add content on top of both generations would increase technical debt and make future regions harder to build consistently.

Therefore the implementation order is deliberately:

1. unify world controls and interactions;
2. unify the exploration shell and fix region geometry;
3. make atmosphere/weather global and coherent;
4. repair race progression and give Crystal Cascade a genuinely distinct presentation;
5. repair the Wonderbook and establish the Valley map;
6. expand the successful Firefly Lantern activity;
7. perform the non-linear world-layout/content-density pass originally intended by WP5.9.

Do not solve these as one giant PR.

---

# Locked design decisions from the playtest

These decisions are approved and should not be re-litigated during implementation unless a concrete technical blocker proves one unsafe or impractical.

1. **Normal region exits are walk-through boundaries.** A player should move into/push against the exit and transition automatically. `E`, `Enter`, click and tap are for NPCs, objects, activities and other intentional interactions, not ordinary travel between exploration regions.
2. **Interactive things use one interaction contract.** NPCs, discoveries, activities and optional gateways should all be invokable through `E`, `Enter`, click and tap where applicable.
3. **Exploration uses one shared world shell.** Bag, Sound, Controls, Hint/suggestion access and other common HUD controls must not be reimplemented independently by each region.
4. **Gallop is a convenience action, not a stamina mechanic.** Default implementation: hold `Shift` on keyboard and an equivalent touch control while moving, at approximately 1.6x normal movement speed. No stamina bar or resource cost.
5. **Atmospheric time is game-time/progression driven, never dependent on the real-world clock.** Automatic mode should visibly cycle on a child-observable timescale; initial target is roughly three minutes per state, subject to playtest tuning rather than silent multi-hour waits.
6. **Weather and atmospheric time apply to all appropriate outdoor exploration regions**, not only newly added scenes.
7. **Magical weather effects live in world space where that visual makes sense.** Sparkle weather should surround the travelling unicorn/world rather than appear glued to the camera/window.
8. **Race progression is gated.** Nova introduction -> first practice/warm-up -> Sunrise Sprint -> Crystal Cascade. Later races must follow explicit unlock conditions instead of all being immediately available.
9. **Crystal Cascade must be visually and mechanically legible as a Crystal Brook race**, not merely Sunrise Sprint with reordered obstacles and a different title.
10. **The Valley map belongs inside the Bag.** It should establish the wider world topology and future destinations. No fast travel is added during this package, but the design should not block a later fast-travel feature.
11. **The Valley should not remain a linear corridor.** Later WP5.9 work must establish branches, side destinations and/or loops while preserving clear child-friendly navigation.
12. **Firefly Lantern remains optional and playful.** Its expanded modes unlock after first completion; rewards should recognise milestones rather than turn the activity into grind.

# Autonomous execution protocol for R5-WP5.9

The following rules are intended to maximise safe autonomous progress across future chats/agent runs.

## Default execution behaviour

For each sub-package A through G, the implementing agent should normally:

1. begin from current `main`;
2. inspect the relevant existing systems before changing architecture;
3. create one focused branch/PR for the sub-package;
4. implement reusable/shared systems rather than scene-specific patches where the package calls for unification;
5. add or update automated tests for regressions that can be expressed mechanically;
6. run formatting, lint, type-check, unit tests, production build and browser/static smoke tests available in the repository;
7. diagnose and fix failures rather than weakening tests to make CI green;
8. review the PR diff for accidental scope creep;
9. squash-merge when CI is green and the PR is mergeable;
10. continue to the next sub-package without requiring fresh planning approval unless a hard-stop condition below is met.

One sub-package should remain one independently diagnosable PR wherever practical. If a sub-package proves too large, split it internally (for example `5.9B1`, `5.9B2`) rather than combining unrelated later work.

## Manual playtest checkpoints

A short human playtest checklist should be produced after each sub-package. These checkpoints are valuable evidence but are **not automatically blocking** autonomous implementation of unrelated later sub-packages.

Stop and wait for manual confirmation before proceeding only when:

- the next sub-package would build directly on a subjective feel/visual decision that cannot be validated mechanically;
- the implementation appears to contradict a locked design decision;
- the user explicitly asks for a stop/checkpoint;
- a newly discovered issue materially changes the planned architecture.

## Hard-stop conditions requiring user input

Pause rather than guess if any of these occur:

- a change would intentionally wipe or incompatibly alter existing saves without a safe migration;
- two locked design decisions become technically incompatible;
- a new feature would materially change the child-facing control scheme beyond the decisions above;
- a required third-party/deployment permission cannot be accessed autonomously;
- CI remains failing after reasonable diagnosis and the only apparent route is to remove/disable meaningful validation;
- a proposed visual/world-layout decision would permanently constrain future geography and there is no clear option consistent with this document;
- implementation discovers that a supposedly shared system is too entangled to refactor safely inside the bounded package.

Otherwise, prefer making the smallest sound decision and documenting it in the PR rather than asking for trivial implementation choices.

# R5-WP5.9A - Unified World Controls and Interaction

Dependencies: R0-WP0.5, R1-WP1.3, completed R5-WP5.1 through R5-WP5.8.

Priority: **First. Do not begin 5.9B implementation until the shared interaction/movement contract is stable.**

Goal:

- make every exploration region obey one player movement, interaction, transition and return-position contract.

Deliverables:

### A1 - Shared interaction contract

- route NPCs, discoveries, activities and optional gateways through the same interaction API;
- support keyboard `E` and `Enter` for interactables;
- support pointer click/tap through the same action path rather than bespoke scene handlers;
- remove known click-only or keyboard-only interaction exceptions where practical;
- ensure interaction prompts reflect the actual supported controls.

### A2 - Walk-through world transitions

- convert ordinary exploration-region travel to overlap/push-through boundary transitions;
- ordinary region exits must not require `E`, Enter or click;
- transition zones should be positioned at a visible hard edge, doorway, gate, path edge or comparable world boundary;
- prevent the player walking visually behind a region entrance where that makes no spatial sense;
- preserve explicit interaction for optional activities such as races/minigames when appropriate.

### A3 - Correct resume/return position

- capture player world position and facing immediately before dialogue/activity entry where appropriate;
- dialogue must not reset the player to the scene's original spawn;
- Firefly Lantern and comparable activities should return the player beside the activity entrance, not the region's generic arrival spawn;
- preserve safe fallback spawn behaviour if a stored return position is invalid.

### A4 - Correct arrival facing

- region gateways define sensible arrival position and facing;
- moving through a left/right/top/bottom connection should normally face the player into the newly entered region rather than back toward the exit;
- add regression coverage for representative opposite-direction transitions.

### A5 - Pointer/touch movement parity

- fix the known Whispering Woods click-navigation failure;
- pointer/touch movement and keyboard movement should control the same player movement layer;
- modal dialogue/activity states must consistently suspend movement regardless of input device.

### A6 - Gallop action

- add a named `Gallop`/equivalent action to the input abstraction;
- keyboard default: hold `Shift` while moving;
- provide touch architecture/control equivalent where the existing touch shell supports it;
- initial movement multiplier approximately 1.6x normal movement;
- no stamina, cooldown or consumable resource;
- gallop must respect the same collision/transition rules as normal movement.

Acceptance:

- an NPC or interactive object can be activated by `E`, Enter and pointer/tap where all are applicable;
- normal region travel requires only movement into the exit boundary;
- no tested ordinary region gateway remains click-only;
- finishing dialogue keeps the player at the interaction location;
- finishing Firefly Lantern returns beside the lantern/activity entry;
- representative region transitions arrive with sensible facing;
- keyboard and pointer/touch movement work in Whispering Woods;
- holding the gallop action increases traversal speed without bypassing collision;
- save/reload and existing quest progression remain intact.

Suggested manual checkpoint:

- traverse every currently connected region in both directions;
- interact with one older NPC and one newer NPC using keyboard and pointer;
- complete Firefly Lantern once and verify return position;
- gallop along a path and into a region exit.

# R5-WP5.9B - Shared World Shell and Region Geometry

Dependencies: R5-WP5.9A.

Goal:

- stop exploration scenes from owning inconsistent copies of global UI behaviour, then align world collision with what the player sees.

Deliverables:

### B1 - Persistent/shared exploration shell

- establish one common exploration HUD/shell for appropriate world scenes;
- Bag, Sound, Controls and Hint/suggestion access remain available consistently across old and new exploration regions;
- region scenes provide world/map content underneath the shared shell rather than recreating global buttons independently;
- common HUD remains fixed to the viewport and does not interfere with world-space weather/effects;
- scene transitions must not duplicate shell components or leak stale controls.

### B2 - Region geometry/collision audit

Audit all current exploration regions, with particular attention to Crystal Brook and Whispering Woods:

- visible river banks match non-walkable water bounds;
- visible paths match walkable collision corridors;
- stepping stones and bridge-like objects match their actual traversability;
- no invisible wall crosses an apparently open path;
- hard visual barriers behave like hard barriers;
- entrances/exits cannot be walked behind when the art presents them as a boundary;
- player cannot become trapped by small collision seams;
- gateway/return spawns do not place the player inside collision.

### B3 - Crystal Brook language/visual consistency

- remove or rewrite instruction text that implies an exploration jump mechanic that does not exist (for example "hop between stones") unless the environment interaction is explicitly implemented without suggesting a general jump control;
- tighten obvious prototype geometry where collision alignment requires the artwork to change;
- ensure water/stone/path composition reads correctly at normal gameplay scale.

### B4 - New-region visual tightening

- perform a bounded presentation pass while geometry is already being touched;
- fix obvious seams, contradictory layering, unreadable entrances and sparse/awkward placement;
- do not attempt the full R6 production-art replacement here.

Acceptance:

- all ordinary exploration areas expose the same global HUD capabilities;
- moving between scenes does not duplicate or lose common controls;
- Crystal Brook visible river/path boundaries agree with collision;
- player cannot walk behind hard-edge gateways shown as blocking structures;
- no known invisible wall blocks an apparently valid main path;
- environment copy does not promise controls/mechanics the player does not have;
- existing story/discovery interactions remain reachable.

Suggested manual checkpoint:

- walk perimeter/path edges in every region;
- deliberately push against rivers, entrances and decorative barriers;
- confirm Bag/Sound/Controls/Hint remain present through several scene transitions.

# R5-WP5.9C - Global Atmosphere and Weather Integration

Dependencies: R5-WP5.9B, R5-WP5.6, R5-WP5.7.

Goal:

- make atmospheric time and magical weather feel like properties of the Valley rather than features attached only to the newest scenes.

Deliverables:

### C1 - Atmosphere coverage

- apply morning/afternoon/sunset/night presentation to all appropriate outdoor exploration regions;
- centralise scene hooks/data sufficiently that future outdoor regions inherit the system with minimal bespoke wiring;
- preserve indoor/activity/race exceptions where atmosphere should not be blindly overlaid.

### C2 - Clear morning/afternoon distinction

- tune palette/lighting/ambient cues so morning and afternoon are visibly distinguishable at a glance;
- maintain readability and avoid relying solely on tiny HUD labels.

### C3 - Understandable automatic time progression

- replace the effectively invisible/overlong auto behaviour with a child-observable game-time cycle;
- initial target: approximately three minutes per state, producing a roughly twelve-minute full cycle;
- cycle: Morning -> Afternoon -> Sunset -> Night -> Morning;
- manual state selection remains available;
- returning to Auto resumes automatic progression in a predictable way;
- do not use real-world clock lockouts.

### C4 - Weather coverage

- apply weather to all appropriate outdoor exploration regions;
- keep manual Clear/Rain/Sparkle selection and Auto behaviour coherent across scene changes;
- avoid duplicated particle systems when moving between regions.

### C5 - World-space sparkle weather

- rework sparkle weather so particles/effects are positioned/spawned relative to the world/player region rather than appearing fixed to the camera glass;
- as the player moves, new effects should occupy the landscape around them naturally;
- clean up off-screen/stale effects for performance.

### C6 - Automatic weather behaviour

- automatic weather state should visibly respond to the atmosphere/time model within normal play duration;
- preserve conditional discovery availability such as Stardew Drop;
- make state transitions testable rather than dependent on waiting an impractically long period.

Acceptance:

- older and newer outdoor regions all show atmosphere/weather where appropriate;
- morning and afternoon are visibly different without reading the state label;
- Auto time visibly advances during a normal play session;
- manual -> Auto returns to working progression;
- rain/sparkle do not duplicate across transitions;
- sparkle effects occupy world space rather than remaining fixed to the viewport;
- Stardew Drop and other weather-conditioned content remain replay-safe;
- performance remains acceptable under active weather.

Suggested manual checkpoint:

- remain in one region long enough to observe an automatic time change;
- traverse old -> new -> old outdoor regions under rain and sparkle;
- gallop while sparkle weather is active and verify the effect belongs to the world rather than the screen.

# R5-WP5.9D - Race Progression and Crystal Cascade Repair

Dependencies: R5-WP5.9A, R5-WP5.9B, existing R3 racing systems, R5-WP5.8.

Goal:

- make racing progression coherent and turn Crystal Cascade into a visibly distinct second course while retaining the reusable race engine.

Deliverables:

### D1 - Race unlock progression

Required order:

1. Nova first introduction;
2. first practice/warm-up race;
3. Sunrise Sprint completion/unlock milestone;
4. Crystal Cascade becomes available.

Implementation requirements:

- Crystal Cascade cannot be entered before its prerequisite progression;
- a locked entrance gives a short child-friendly clue about what to do next rather than silently failing;
- unlock state persists across reload;
- existing completed saves should migrate/derive a sensible unlock state rather than being unnecessarily reset.

### D2 - Crystal Cascade region-specific presentation

Keep the shared race engine, but provide a genuinely different course presentation using Crystal Brook identity:

- Crystal Brook water/current motifs;
- crystal formations and sparkle accents;
- reeds and riverbank dressing;
- driftwood/log obstacles that actually look like driftwood/log obstacles;
- reed hurdles that visually read as reed hurdles;
- watery/prismatic boost currents rather than generic copied strips;
- a distinct course palette/background composition;
- distinct start/finish dressing;
- obstacle visuals aligned with collision/hitboxes.

### D3 - Prism Current route variation

- make the Prism Current shortcut/alternate route visually discoverable;
- communicate that it is advantageous through course design/effects, not explanatory text alone;
- ensure it actually changes the player's route/speed experience enough to justify being called a shortcut/variation;
- AI must remain able to finish reliably regardless of whether it uses the shortcut.

### D4 - Race identity and persistence regression

- Sunrise Sprint must continue to load its original course/presentation;
- Crystal Cascade results, ribbons and best times remain separate;
- course selection must not leak across races;
- finish/return route must return to the correct region;
- Crystal Cascade reward edge cases from manual section 8 should be re-run after the visual/progression repair.

Acceptance:

- new player cannot attempt Crystal Cascade before the intended Nova/practice/Sunrise progression;
- locked Crystal Cascade explains the prerequisite in child-friendly language;
- Crystal Cascade is recognisable as Crystal Brook from a screenshot without relying on the title text;
- driftwood/reed/current objects named by course data have matching visible art;
- Prism Current is visible and worthwhile;
- Sunrise Sprint remains unchanged by Crystal-specific presentation;
- race records/rewards remain separate and persistent;
- repeated race/region transitions do not leak course selection or scenery.

Suggested manual checkpoint:

- test on a fresh/new progression path through Nova -> practice -> Sunrise -> Crystal;
- compare one Sunrise screenshot and one Crystal screenshot side by side;
- rerun Crystal Cascade result/reward tests 8.8 onward.

- repair the increasingly crowded Wonderbook UI and create an in-game Valley map that establishes non-linear world geography before more regions are built.

Deliverables:

### E1 - Wonderbook pagination/layout repair

- contain discovery entries inside the visible left/right pages;

- correct page-turn direction so left/right behaviour matches the visual metaphor;
- make page controls reliably clickable/tappable;
- ensure keyboard/controller abstraction can be added or used consistently where already supported;
- prevent discovery notifications/toasts from obscuring essential entries or the close/page controls;
- retain all existing discovered entries and persistence.

### E2 - Map inside Bag

- add a `Map` section/tab within the Bag/inventory experience;
- show the player's home/current core regions in a coherent Valley overview;

- establish room for future regions as faded/locked/unrevealed nodes rather than extending the UI as a straight list;

- home should be easy to recognise on the map.

### E3 - Canonical Valley topology

The map becomes the design source for future physical region relationships.

Requirements:

- current world should no longer be represented conceptually as one endless linear chain;
- introduce branches, side destinations and/or loops in the planned topology;
- avoid geographically confusing connections even if not all future regions are implemented yet;
- locked/future regions may appear as silhouettes/clouds/question-mark destinations where suitable;
- do not promise a specific named future region unless already supported by the wider roadmap/design docs.

### E4 - Fast-travel readiness, but no fast travel yet

- structure map data/region IDs so a later fast-travel system could reuse it;
- do not let the player teleport from the map in WP5.9E;
- no map interaction should bypass quest/race progression or physical exploration.

Acceptance:

- no Wonderbook entry renders below the intended page area;
- page navigation direction and click/tap behaviour are intuitive;
- all existing discoveries remain represented after reload;
- Bag contains a usable Valley map;
- current region/home are identifiable;
- map topology contains at least one branch/side relationship rather than a single corridor;
- unimplemented destinations can be represented without breaking navigation;
- map cannot yet be used for fast travel.

Suggested manual checkpoint:

- open the fullest available Wonderbook page and navigate forward/back repeatedly;
- open Bag -> Map from several regions and confirm orientation makes sense without external explanation.

# R5-WP5.9F - Firefly Lantern Modes and Rewards

Dependencies: R5-WP5.9A (return-position and unified interaction), existing R5-WP5.5.

Goal:

- preserve the successful Firefly Lantern core, fix its completion/reward clarity, and turn it into a small replayable activity with three distinct modes after first completion.

Deliverables:

### F1 - Base activity repair

- if all eight target fireflies are collected, do not show text claiming missed lights wandered back;
- provide clear first-completion feedback;
- award/record a visible first-completion reward or milestone;
- return to the actual lantern/activity entry position in Whispering Woods;
- ensure repeat play cannot duplicate unique first-completion rewards incorrectly.

### F2 - Mode selection unlocked after first completion

First-ever play remains simple Normal mode with minimal extra menu friction.

After first completion, expose:

1. `Normal`
2. `Multicolour`
3. `Endless`

Mode selection must remain understandable to a young player with short labels/visual explanation.

### F3 - Normal difficulty levels

Normal objective remains: collect eight target fireflies.

Provide a small number of difficulty tiers (initial target: three) by tuning combinations of:

- firefly lifetime before disappearing;
- target size/size variance;
- spawn cadence/movement as supported by the activity engine.

Avoid a complicated settings screen. Difficulty should be recognisable and replayable.

### F4 - Multicolour mode

- yellow fireflies are the targets;
- other-colour fireflies appear as decoys;
- collecting a decoy counts as a mistake;
- initial failure model: allow three mistakes before ending the attempt rather than instant failure;
- objective remains collecting eight valid yellow targets;
- visual feedback must make correct/incorrect catches immediately obvious.

### F5 - Endless mode

- begins at roughly Normal/easy pacing;
- has no fixed collection target;
- gradually increases pressure through faster cadence, shorter lifetime, smaller targets and/or other existing safe parameters;
- missing a target ends the run;
- save a personal best score;
- restarting should be immediate and low-friction.

### F6 - Milestone rewards

Use finite achievement-style rewards, not an exploitable grind loop.

Provide persistent milestones for, at minimum:

- first Normal completion;
- first Multicolour completion;
- a meaningful Endless score threshold;
- optionally one higher Endless mastery threshold if play balance supports it.

Prefer Wonderbook entries, cosmetic/accessory items or cottage decorations over repeatedly farmable large Shimmer payouts. Ordinary repeat play may give modest feedback/currency only if it remains generous and non-grindy.

Acceptance:

- perfect Normal completion never shows missed-firefly text;
- first completion clearly grants/records a reward or milestone;
- first completion unlocks the three-mode selector;
- Normal difficulty tiers are mechanically different but still recognisably the same game;
- Multicolour penalises wrong-colour catches and remains recoverable up to the defined mistake limit;
- Endless increases difficulty over time and ends on a missed target;
- Endless personal best persists across reload;
- unique milestone rewards cannot duplicate incorrectly;
- exiting any mode returns to the lantern location and normal Woods exploration.

Suggested manual checkpoint:

- complete each mode at least once;
- intentionally catch decoys in Multicolour;
- intentionally miss an Endless target;
- reload and confirm personal best/milestones remain.

# R5-WP5.9G - Non-linear World Layout and Content Density Pass

Dependencies: R5-WP5.9A through R5-WP5.9F, especially the canonical map topology from R5-WP5.9E.

Goal:

- complete the original WP5.9 purpose by making traversal itself interesting and ensuring the growing Valley does not feel like a sequence of long corridors between isolated markers.

Deliverables:

### G1 - Layout/topology implementation pass

- use the Valley map as the canonical intended topology;
- where safe without rewriting established story content, introduce branches, side paths and loops between/within regions;
- not every region should sit directly before/after exactly one other region;
- preserve clear landmarks and child-friendly route cues;
- do not create maze-like navigation for the sake of non-linearity.

### G2 - Dead-zone audit

For each exploration region:

- identify stretches with no visual, interactive or navigational purpose;
- shorten/recompose dead traversal where appropriate;
- add small discoveries, ambient reactions, scenery moments, optional pockets or alternate paths where they materially improve exploration;
- avoid filling every screen with UI markers or compulsory chores.

### G3 - Revisitation check

- confirm each major region has at least one reason to revisit after its first story beat;
- use discoveries, activity access, weather/time conditions, race access, character state or visual world changes where already supported;
- do not add grind solely to manufacture revisitation.

### G4 - Orientation and return-home check

- verify players can use landmarks plus the Bag map to understand where they are and how areas relate;
- returning toward home should be understandable even when the topology branches;
- no fast travel yet, so physical routes must remain tolerable with normal movement and gallop.

### G5 - Performance and persistence sweep

- verify the larger set of world managers, weather effects, shell UI and discoveries do not create severe frame-rate or transition degradation;
- check representative long-running save/reload behaviour;
- ensure completed content does not regress or duplicate rewards after repeated revisits.

Acceptance:

- current world topology is not purely linear;
- major regions contain meaningful side-space/optional exploration without becoming cluttered;
- no major route consists of an excessive empty walk between isolated quest points;
- map and physical connections agree;
- revisiting regions exposes useful content/state rather than only empty scenery;
- player can orient toward home without external explanation;
- performance remains acceptable across repeated region changes with atmosphere/weather active;
- R5 release gates pass.

Final manual R5 checkpoint:

- start from home/new-game-compatible state and explore without a prescribed test route;
- deliberately take side paths;
- use the map only when naturally needed;
- play one race and Firefly Lantern;
- observe at least one automatic atmosphere/weather transition;
- return home physically;
- close/reload and confirm the world state still makes sense;
- record confusion, delight, repeated activities and anything that still needs adult explanation.

# Package dependency / execution order

Default order:

`R5-WP5.9A -> R5-WP5.9B -> R5-WP5.9C -> R5-WP5.9D -> R5-WP5.9E -> R5-WP5.9F -> R5-WP5.9G`

Reasoning:

- A establishes the player/input/transition contract everything else must use.
- B establishes the shared exploration shell and trustworthy collision geometry.
- C can then apply global atmosphere/weather through the stable shell/region architecture.
- D relies on the unified interaction/transition patterns and fixes the largest content regression from WP5.8.
- E repairs a known UI failure and establishes the canonical world topology before map/layout expansion.
- F expands a proven fun activity only after its return/input behaviour is repaired.
- G uses all of the above to reshape traversal/content density rather than adding more features on an unstable base.

Parallel work is allowed only when two changes genuinely do not touch the same shared systems and cannot create conflicting assumptions. Prefer sequential merges over speculative stacking.

# R5-WP5.9 completion gate

R5-WP5.9 is complete only when:

- A through G are merged;
- repository validation is green on `main`;
- old and new exploration regions use the same interaction/movement/HUD conventions;
- region collision is visually trustworthy;
