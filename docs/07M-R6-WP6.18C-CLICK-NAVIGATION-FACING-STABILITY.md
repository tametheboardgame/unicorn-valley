# R6-WP6.18C - Click-Navigation Facing Stability

## Playthrough finding

The R6-WP6.18 human playthrough found that point-and-click movement could make the player unicorn flick rapidly between opposing horizontal facings while following a backwards route.

## Root cause

Exploration scenes own movement and facing through `PlayerEntity`, but `ClickToMoveManager` previously updated only the Phaser sprite after the scene update had completed. That left `PlayerEntity` holding the old facing. On the next frame the scene reapplied that old facing before click navigation flipped the sprite again.

The result was two movement layers disagreeing about the same player state.

## Remediation

- `PlayerEntity` now maintains a weak sprite-to-entity registry for shared input systems.
- Click navigation resolves facing from its actual path direction and writes it through the authoritative `PlayerEntity` when one exists.
- A safe direct-sprite fallback remains for supported scenes that do not use `PlayerEntity`.
- Near-zero waypoint deltas preserve the previous facing instead of introducing a meaningless direction change.
- Keyboard/touch movement still uses the existing scene-owned movement path and can cancel click navigation normally.

## Regression coverage

- Pure unit tests cover stable backwards facing, meaningful direction changes and defensive facing parsing.
- Browser diagnostics expose both rendered sprite facing and authoritative `PlayerEntity` facing.
- The browser regression first establishes a right-facing player, clicks back to the left, samples the route repeatedly and requires rendered and authoritative facing to remain left throughout. It then verifies keyboard movement can take control and face right again.

## Boundary

This package does not redesign movement speed, pathfinding, collision, controls or animation. It fixes state ownership for click-navigation facing only.

The R6-WP6.18 human-feedback hard stop remains active after this package.
